## 1. 무엇이 막혀 있나 — 실측

```
data/approved/labor-mappings.json    매핑 1,331건 전부 confirmed: false
schema.ts:114                        confirmed: z.literal(false)   ← true 가 들어갈 수 없다
calculateLabor.ts:121                !mapping.confirmed → blocking: true 경고
```

**거의 모든 견적 행에 `mapping-unconfirmed` 차단 경고가 뜬다.**
`priceQuote.ts:82` 도 *"품셈 경고에는 `mapping-unconfirmed` 가 거의 항상 들어 있다"* 고 적고 있다.

### ⛔ 정정 — 매핑은 "기계가 추측한 연결"이 아니다

내가 사용자에게 *"품셈 연결을 프로그램이 자동으로 맞춘 것이라 기계가 추측한 것"* 이라고
설명했다. **부정확했다**(Codex 지적). 코드를 확인했다.

```
buildLabor.ts:140-151
  laborMappingId: sku
  sku
  laborItemId: sku          ← 같은 SKU. 즉 원본의 같은 행이다
  conversionFactor: '1'     ← "품셈 기준 단위와 판매 단위가 같은 행에서 왔으므로 환산이 없다"
```

**원본 엑셀의 같은 줄에서 제품 정보와 품셈 정보를 함께 읽은 것이다.**
제품 행에 품셈 코드와 직종별 공수가 같이 적혀 있어서, 그 행 안에서 연결된다.
**"어느 품셈을 쓸지 기계가 골라 맞춘" 것이 아니다.**

`confirmed: false` 는 `MAPPING_NOTE` 가 말하는 **정책**이다.

> *"표준품셈 통합문서에서 자동 추출. 사람이 확인하기 전까지 확정에 쓰지 않는다."*

즉 **"사람 눈을 거치지 않았다"** 는 뜻이지 **"추측으로 맞췄다"** 는 뜻이 아니다.

→ 사용자에게 이 정정을 전달했다.

### 화면에는 그것을 풀 수단이 없다

```
LaborMode = 'mapped' | 'manual' | 'not-applicable' | 'unresolved'    타입은 있다
manualLaborUnitPrice · overrideReason                                 필드도 있다

QuoteSheet.tsx:160·239   not-applicable 을 **표시만** 한다
                         설정하는 버튼·입력이 없다
```

→ **작업 파일 JSON 을 손으로 고치지 않으면 견적을 완결할 수 없다.**
  그것은 기계적 시험용 우회일 뿐 제품 완료가 아니다.

## 2. 설계 제안 — 기존 정책으로 정할 수 있는 것은 여기서 정한다

Codex 요청: *"기존 정책·사용자 지시로 정할 수 있는 구현사항은 또 묻지 말고 제안해
검토 요청"*. 아래는 **내 제안**이다. 검토에서 뒤집히면 따른다.

### 2-1. 확인은 **견적 행**에 묶는다. 전역 카탈로그를 건드리지 않는다

```
⛔ data/approved/labor-mappings.json 의 confirmed 를 true 로 바꾸지 않는다
⛔ schema.ts 의 z.literal(false) 를 풀지 않는다
✅ 확인 사실은 QuoteRow 안에 둔다
```

**이유:** 배포 자료는 "자동 추출이고 미확인"이라는 사실을 그대로 유지해야 한다
(`buildLabor.ts:13` · 설계서 §5.3). 한 견적에서 확인했다고 **다른 모든 견적에서
확인된 것으로 바뀌면 안 된다.**

### 2-2. 확인은 **내용 지문**에 묶는다. 내용이 바뀌면 무효가 된다

`QuoteRow` 에 아래를 더한다.

```ts
laborConfirmation?: {
  /** 무엇을 보고 확인했는지 — 아래 값들을 이어 붙인 지문 */
  basisFingerprint: string;
  confirmedAt: string;        // ISO 날짜
};
```

**지문에 들어가는 것** (하나라도 바뀌면 확인이 풀린다):

```
제품 identity    rowId · productId/SKU
품셈 연결        laborMappingId · laborItemId · 품셈 코드
공수            직종별 (직종명 + 수량)   ← 직종을 정렬해 순서를 고정한다
노임            적용된 직종별 금액 + wageTableId
단위            wageUnit(M/D·M/M) · 품셈 baseUnit · 견적 행 unit
계수            품목별 요율 · 할증 · conversionFactor
수량            행의 quantity
규칙            계산 rule 버전 (DocumentVersions.rule)
```

⚠ **`conversionFactor` 와 단위를 반드시 넣는다**(Codex 지적). 공수와 노임이 똑같아도
**환산 계수가 달라지면 금액이 달라진다.** 지금은 같은 행에서 왔기 때문에 `'1'` 이지만
(`buildLabor.ts:144`), 나중에 품셈 단위와 판매 단위가 다른 매핑이 생기면 달라진다.

⚠ **제품 identity 를 넣는 이유는 확인이 다른 행·다른 제품으로 복사되는 것을 막기
위해서다.** 같은 품셈을 쓰는 두 행이 있어도 **각각 확인해야 한다.**

- [ ] `Decimal` 값을 **정규화**해 문자열로 만든다(`'0.30'` 과 `'0.3'` 이 같은 지문이어야 한다).
- [ ] 직종을 **정렬**한다. 원본 순서가 바뀌어도 지문이 달라지면 안 된다.
- [ ] **구조를 직렬화**한다. 값들을 그냥 이어 붙이면 경계가 모호해진다.
- [ ] ⛔ **`confirmedAt`(확인 시각)은 지문에 넣지 않는다.** 시각이 들어가면 같은 근거라도
      지문이 매번 달라진다.

→ 품셈이 바뀌거나 노임이 갱신되면 **지문이 달라져 확인이 자동으로 무효**가 된다.
  사람이 "그때 그 숫자를 보고" 확인한 것이므로, 숫자가 바뀌면 다시 봐야 한다.

### 2-3. 세 가지 상태를 사람이 고른다

| 고르는 것 | 뜻 | 필요한 입력 |
|---|---|---|
| **확인함** | 품셈 연결과 계산 근거를 보고 맞다고 판단했다 | 없음 (지문이 자동 기록됨) |
| **직접 입력** (`manual`) | 품셈 대신 금액을 직접 넣는다 | 금액 + **사유**(설계서 §5.3) |
| **해당 없음** (`not-applicable`) | 이 행에는 노무가 들어가지 않는다 | **사유** |

- [ ] ⛔ **기본값은 어느 것도 아니다.** 아무것도 고르지 않으면 **차단이 유지**된다.
- [ ] ⛔ **일괄 확인 버튼을 만들지 않는다.** 행마다 사람이 본다.
      (설계서 §7.5 — 미확인을 확인 완료로 바꾸지 않는다)

### 2-4. 확인하기 전에 **근거를 보여준다**

고르기만 하는 화면이면 사람이 무엇을 확인했는지 모른다. **계산 과정을 펼쳐 보인다.**

```
HD PTZ Camera / BRC-AM7            품셈 7-11-1-방송용카메라

  통신관련기사      0.15 × 324,979 =  48,746.85
  통신관련산업기사   0.35 × 304,662 = 106,631.70
  통신설비공       0.20 × 316,875 =  63,375.00
  보통인부        0.31 × 172,698 =  53,536.38
                            합계  272,289.93
  × 품목별 요율 0.63              = 171,542
  × 할증 (없음)
  × 수량 1                       = 171,542

  노임 기준  26년 하반기 (가이드)        [확인함] [직접 입력] [해당 없음]
```

- [ ] 노임이 **어느 표에서 왔는지** 함께 보여준다. 배포본과 가이드가 다를 수 있다
      (`workspace.ts:135`).
- [ ] ⛔ 금액만 보여주고 고르게 하지 않는다.

#### 표시 순서를 계산 순서와 맞춘다 (Codex 지적 4)

```
Σ(공수 × 노임)  →  × (1 + 할증)  →  × 품목별 요율  →  × conversionFactor
                →  최종 INT  →  × 수량
```

- [ ] ⛔ **중간 단계에서 절사하지 않는다.** 보여줄 때도 계산할 때도 마찬가지다.
      화면이 중간 절사를 하면 사람이 확인한 숫자와 실제 금액이 어긋난다.

#### 보여준 근거와 **확인을 누른 순간**이 같아야 한다

- [ ] 확인을 누를 때 **그 자리에서 지문을 다시 계산해 비교**한다.
      펼쳐 놓은 패널이 옛 숫자를 보여주는 동안 뒤에서 기준이 바뀌었을 수 있다.
      **같지 않으면 확인을 받지 않고** 새 숫자를 다시 보여준다.
- [ ] ⛔ **옛 패널의 숫자를 보고 누른 승인을 받아들이지 않는다.**
- [ ] 계산이 **`basis-conflict` 상태이면 확인 자체를 할 수 없게** 한다.
      기준이 어긋난 상태에서 본 숫자는 근거가 되지 않는다.

#### 확인이 풀렸을 때의 안내

- [ ] 무효가 된 **원인 스냅샷이 있으면** 무엇이 바뀌었는지 적는다.
- [ ] ⛔ **스냅샷이 없으면 원인을 추측해 적지 않는다.**
      *"계산 근거가 바뀌어 다시 확인이 필요합니다"* 같은 **일반 문구**를 쓴다.
      *"노임표가 바뀌었습니다"* 라고 단정했는데 실제 원인이 다르면 사람을 잘못 이끈다.

### 행이 바뀔 때 확인·금액·사유가 어떻게 되는지 정한다

```

행 복제          → ⛔ 확인을 복사하지 않는다
삭제 후 재생성    같은 rowId 가 다시 남   → 확인 버림
명시적 재계산     → 지문 비교로 판정
mode 전환        mapped ↔ manual ↔ not-applicable
                → 전환하면 이전 상태의 금액·사유를 **남기지 않는다**
```

- [ ] ⚠ **`withResolvedProduct` 가 `...rest` 로 필드를 넘긴다**(`resolveProduct.ts`).
      새 확인이 붙거나 **옛 `manualLaborUnitPrice` 가 남을 수 있다.** 그 경계를 시험한다.

### 저장·복원 경로도 같이 막는다

- [ ] 작업 파일 **decode 경로**와 **도메인 직접 경로**(서버 없이 함수를 바로 부르는 길)
