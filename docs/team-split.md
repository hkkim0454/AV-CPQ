### ⛔ 코드를 고치는 세션은 하나뿐이다

세 세션의 **작업 폴더가 모두 같다.**

```
C:\Users\khk00\Desktop\paseo project\AV-CPQ
```

둘 이상이 동시에 파일을 고치면 **서로 덮어쓴다.** Git 브랜치로도 해결되지 않는다.
브랜치는 여럿이어도 **작업 트리는 하나**라서, 한쪽이 브랜치를 바꾸면 다른 쪽이
작업 중인 파일이 통째로 바뀐다.

→ **구현은 Claude Code 한 곳에 모은다.** 이것이 이 구조를 쓰는 가장 큰 이유다.

> **사용자 판단으로 철회했다.** 같은 폴더에서 둘이 코드를 고치는 위험이 얻는 것보다 컸다.

## 2. 작업 순서

```
  ① 사용자 지시·자료
        ↓
  ② 계획 세션   사실 확인 → 결정 기록 → 계획서 작성
        ↓
  ③ Codex      계획 검토 · 빠진 것·위험·모순 지적
        ↓
  ④ 계획 세션   지적 반영. 사용자 판단이 필요하면 질문
        ↓
  ⑤ Claude Code  구현 (시험 먼저 → 코드 → 검증 → 커밋)
        ↓
  ⑥ Codex      구현 결과 독립 검토
        ↓
  ⑦ 계획 세션   결정 기록과 코드 대조 · 인수 기록
        ↓
  ⑧ 사용자     푸시 승인
```

### 지시는 Codex 를 거친다

구현 지시를 **Claude Code 에 직접 보내지 않는다.** 계획 세션이 Codex 에 보내고,
Codex 가 검토한 뒤 Claude Code 에 전달한다.

이유는 **검토 없이 바로 구현되는 것을 막기 위해서다.** 계획 세션이 혼자 판단한
내용에 오류가 있을 때 중간에서 걸린다. 실제로 여러 번 걸렸다.

---

## 3. 각 세션이 하지 않을 것

### 계획 세션

- 코드를 고치지 않는다. `docs/` 만 쓴다.
- **확인하지 않은 것을 확인한 것처럼 쓰지 않는다.** 읽은 범위를 함께 적는다.
- 사용자에게 같은 질문을 반복하지 않는다.
- 푸시는 사용자 승인 뒤에만 한다.

### Codex

- 코드를 직접 고치지 않는다. 지적하고 돌려보낸다.
- 계획 세션이 전한 내용을 **그대로 믿지 않는다.** 독립적으로 확인한 것과 구분해 적는다.

### Claude Code

- **계획에 없는 것을 임의로 넣지 않는다.** 필요하면 먼저 알린다.
- 시험을 지우거나 건너뛰지 않는다. 실패를 통과로 만들지 않는다.
- **역방향 시험을 넣는다** — 검사를 일부러 깨뜨렸을 때 걸리는지 확인한다.
  이것이 없으면 "검증 통과"는 근거가 되지 않는다(제어 문자 사건).
- 한 Task 가 끝날 때마다 커밋한다. 여러 Task 를 한 커밋에 섞지 않는다.
