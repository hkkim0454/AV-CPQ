# 계산 기준 관리 화면 Implementation Plan (O22)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. 이 계획은 `2026-10-04-quote-workspace-ui.md` 의 **Task 7 이 끝난 뒤** 착수한다. 견적 화면과 동시에 고치지 않는다.

**Goal:** 견적 금액을 정하는 세 가지 기준(공수·노임·간접비 요율)이 지금 무엇으로 적용되고 있는지 사람이 화면에서 **보고**, 새 자료로 **바꾸고**, 바꾸기 전에 **무엇이 얼마나 달라지는지 확인**할 수 있게 한다.

**Architecture:** 기준은 세 축이 서로 다른 주기로 바뀌므로(결정 D20) **각각 독립 버전·독립 교체**한다. 화면은 기준을 읽고 교체 후보를 검증할 뿐, 계산식을 복제하지 않는다. 기존 견적은 사용자가 **명시적으로 재계산을 누를 때만** 바뀐다.

**Tech Stack:** 기존 React 19.2 / TypeScript 5.9 / Vite 7.1 / decimal.js / Zod / Vitest / Playwright. 새 런타임 라이브러리를 추가하지 않는다.

**Spec:** `docs/decisions/2026-10-03-scope-and-data.md` D1·D12·D17·D20, `docs/design-spec.md` §5.4·§6.3, `docs/stage-status.md` O22.

## 1. 왜 이 화면이 필요한가 — 확인한 사실

착수 전에 코드를 직접 읽고 확인했다. 아래는 **추정이 아니라 실측이다.**

### 세 기준이 서로 다른 곳에 산다

| 기준 | 지금 어디에 있나 | 바꾸려면 |
|---|---|---|
| **공수**(품) | `data/approved/labor-items.json` — 1,331건 | 품셈 엑셀 재추출 후 파일 교체 |
| **노임** | `data/approved/wage-table.json` — 직종별 단가 | 같은 추출 경로로 파일 교체 |
| **간접비 요율** | **`src/domain/quote/indirectCosts.ts` — 소스 코드** | **TypeScript 를 고치고 다시 빌드** |

세 번째가 특히 문제다. 요율 9항목이 **데이터가 아니라 프로그램 코드 안에** 적혀 있어서,
숫자 하나를 바꾸려 해도 개발자가 코드를 고치고 배포해야 한다.

### 노임표가 두 벌 있고, 어느 쪽이 쓰이는지 화면에 안 보인다

```
data/approved/wage-table.json      wageTableId "WAGE-26년 상반기"   ← 배포본
견적서 가이드 3행                    26년 하반기                      ← 실제 계산에 쓰는 것
```

`src/app/workspace.ts:135` 와 `src/app/resources.ts:28` 이 **가이드(하반기) 쪽을 쓴다**고
적고 있다. 계산은 맞게 돌아간다. 다만 **사용자는 두 벌이 있다는 것도, 어느 쪽이
적용됐는지도 화면에서 볼 수 없다.** 이 화면이 그것을 보여준다.

### 2026-10-05 현재 사용자가 겪는 상황

현규님이 26년 하반기 노임 공표 PDF 와 표준품셈 PDF 를 올려 주셨고, 메인 화면에서
**보기·내려받기**는 된다(커밋 `30c9dca`). 그러나 **그 PDF 의 숫자를 프로그램이 쓰는
기준으로 반영하는 경로는 없다.** 지금은 파일을 직접 고치는 수밖에 없다.

## 2. Global Constraints

- **⛔ "파일 하나만 바꾸면 전체가 갱신된다"고 약속하지 않는다.** 품셈 엑셀 입력 지원·자동
  추출·SKU 매핑 갱신은 **아직 설계되지 않았다**(O12 미매칭 105건이 그 증거다).
  이 화면은 **이미 추출이 끝난 자료를 교체**하는 데까지만 책임진다.
- 세 축을 하나의 "기준 버전"으로 묶지 않는다. 결정 D20 — 노임은 반기마다, 공수는 품셈
  개정 때, 요율은 발주처 정책에 따라 **각각 다른 때에** 바뀐다.
- 기존 견적 문서를 **자동으로 재계산하지 않는다.** 기준을 바꿔도 이미 만든 견적은 그대로
  두고, 열 때 차이를 알려 준 뒤 사용자가 고르게 한다(Task 4 저장·열기 경로 재사용).
- 금액 계산식을 이 화면에 복제하지 않는다. 미리보기도 **도메인 계산 함수를 그대로 호출**해
  얻는다.
- 원가·매입처는 이 화면에 들어오지 않는다. 기준은 **판매가·노무비 산정** 자료다.
- 교체 전 자료를 덮어쓰지 않는다. 되돌릴 수 있어야 한다.
- `undefined` 는 미등록이고 `0` 은 0이다(설계서 §5.6). 새 자료에 직종이 빠졌으면
  **0원으로 채우지 않고 막는다.**
- `M/D` 와 `M/M` 을 섞지 않는다(결정 D1 — 섞으면 약 20배 틀린다). 교체 자료의 단위가
  기존과 다르면 **자동 환산하지 않고 거부한다.**

## 3. 사용자 흐름

1. 메인 화면에서 **계산 기준** 으로 들어간다.
2. 지금 적용 중인 **공수·노임·요율** 세 가지를 각각 본다. 각 항목에 **무엇이 출처이고
   언제 만들어졌는지**가 함께 보인다. 노임은 **배포본과 가이드 중 어느 쪽을 쓰는지**
   명시된다.
3. 바꾸고 싶은 축 하나를 고르고 새 자료 파일을 선택한다.
4. 프로그램이 **먼저 검사한다.** 형식·직종 누락·단위 불일치·금액 형식을 보고, 하나라도
   어긋나면 **무엇이 몇 번째 줄에서 어긋났는지** 보여주고 적용을 막는다.
5. 검사를 통과하면 **무엇이 달라지는지** 표로 보여준다. 추가·삭제·금액 변동 직종을
   나란히 놓는다.
6. 사용자가 **적용**을 눌러야 바뀐다. 누르기 전에는 아무것도 바뀌지 않는다.
7. 적용 후, 지금 열려 있는 견적이 있으면 **"새 기준으로 다시 계산하시겠습니까"** 를
   묻는다. 거절하면 견적은 **옛 기준 그대로** 둔다.
8. 되돌리기를 누르면 직전 기준으로 돌아간다.
