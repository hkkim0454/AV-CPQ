## 카탈로그 추출 결과 (커밋 `71f321b`)

```
제품 1468   판매단가 1444   품셈코드 1347
품셈 항목 1331   매핑 1331   매핑 없음 137
노임 21직종 (M/D 17 + M/M 4)
```

판매단가가 계획서 예상 1442 가 아니라 **1444** 다. 차이 2건(`AUD-0085`, `VCF-0035`)은
**명시적으로 입력된 0원**이다. 설계서 §5.6 의 "0원은 명시적으로 입력된 유효한 0과 구분한다" 에
따라 유효값으로 담았다. 숫자가 늘어난 것이 아니라 **분류가 다르다** — 사전 조사가 `>0` 으로 셌다.

매핑 없음 137 = 품셈 코드 없음 121 + 코드는 있으나 품 값이 없는 16(`PIGTAIL` 8,
CMS 의 `IT 기획자`·`IT PM`·`SW아키텍트` 등 8). 후자도 매핑을 만들지 않고 보고만 한다 —
만들면 노무비 0원이 조용히 들어간다.

## 계획을 쓸 때 전제로 깔 사실

### 간접비 28~30행은 "원본 그대로 상수 0"으로 이미 구현됐다

원본 실측 (시스템 시트 5개 전부 동일):

```
28행 연금보험료         E28 = 0.01215   J28 = 0   ← 상수, 수식 아님
29행 건강보험료         E29 = 0.00957   J29 = 0   ← 상수
30행 노인장기요양보험료  E30 = 0.00124   J30 = 0   ← 상수
```

나머지 6개(간접노무비·고용보험료·산재보험료·산업안전보건관리비·퇴직공제부금비·공과잡비)는 `=INT(...)` 수식.

구현:

```ts
interface IndirectCostRule {
  rate: DecimalText;   // 0.01215 — 미적용이어도 보존
  applied: boolean;    // false
  basis: IndirectBasis;
  source: string;
}
```

`applied: false` 면 exporter 가 J열에 **상수 0** 을 쓰고 수식을 쓰지 않는다. 요율은 E열에 남는다.
기본값은 원본과 동일(적용 6 / 미적용 3)이며 **자동으로 켜지 않는다.**

`mapping.md` Ruling R3:

> 요율은 적혀 있으나 금액 칸이 상수 0 이다. **이 견적 1건에서 미적용이라는 뜻이지 법정 미적용이 아니다.**

→ **발주처 프로파일(O7) 설계의 출발점.** `IndirectCostRule[]` 이 시스템마다 붙어 있으므로,
프로파일은 "이 배열을 통째로 갈아끼우는 것"이면 깔끔하다. 시스템별로 다른 프로파일도 이미 가능하다.

### 직접비계 SUM 은 항상 첫 품목 행부터 쓴다

원본은 시트마다 시작 행이 다르다(G5/G6/G7). 그룹 머리글 행에 숫자가 없어 결과는 같지만
일관성이 없다. 생성기는 **항상 첫 품목 행**부터 쓴다 (`mapping.md` R2).

### 노임 단위 불일치는 차단하되 던지지 않는다

품셈 항목의 단위와 노임 단위가 어긋나면 `wage-unit-mismatch` + `blocking: true` 경고를 세우고,
해당 직종 금액과 적용 단가를 **0 으로 둔다.** 조용히 환산하지 않는다 — 환산은 사람이 지정한
`conversionFactor` 만 쓴다. 던지지 않는 이유: 1,468건 중 한 건 때문에 카탈로그 빌드 전체가
멈추면 안 되고, 사용자가 봐야 하는 것은 "이 제품 하나가 막혔다"이기 때문. 커밋 `1701584`.

### Task 완료 조건은 "테스트 통과"가 아니라 "typecheck + 테스트 + audit"이다

실제로 물린 사례. `InternalLine` 에 `sellingUnitPrice` 가 없어서 내부용 표의
**판매단가 열이 통째로 비어 있었다.** 테스트 12개가 전부 통과했고 Excel 검증도 통과했다.
빈 셀은 유효한 XML 이라 어디서도 안 걸린다.

잡은 것은 `tsc -p tsconfig.app.json --noEmit` 하나뿐이다
(`noUncheckedIndexedAccess`, `exactOptionalPropertyTypes` 를 켜 둔 덕).

→ **새 계획의 각 Task 완료 조건에 "테스트 통과"만 쓰지 않는다.**
   `npm run verify`(typecheck → test → audit:exports)로 적는다.
   테스트만으로는 **"값이 아예 안 들어간"** 종류를 못 잡는다. 틀린 값은 테스트가 잡지만,
   없는 값은 테스트가 애초에 쳐다보지 않는다.

### 내부용 → 고객용 방향은 한쪽뿐이다

내부용은 고객용 통합문서에 원가 시트를 **덧붙인다**. 내부용에서 뭔가를 지워 고객용을 만드는
경로가 코드에 **없다**. 지우는 방식은 하나만 빠뜨려도 원가가 고객에게 간다.
설계서 §8.7 "원가 통합문서를 만든 후 열만 숨겨 고객용으로 보내지 않는다" 의 구현이다.

`buildQuoteWorkbook` 의 `extraSheets` 옵션을 고객용 경로는 넘기지 않으며, 시트 수 검사가 고정한다.
새 출력 경로를 만들 때 이 방향을 뒤집지 않는다.

### 수식 셀은 형태를 먼저 조사한다

카탈로그 추출에서 실제로 물린 함정이다. 품 열에 `=0.23*80%`, `=0.63*(1+(2-1)*30%)`,
`=(0.46+0.33+0.52)*(1+(2-1)*30%)` 같은 식이 **585건** 있었다. 전부 **셀 참조가 없는 순수 산술식**이다.

수식이라는 이유로 건너뛰면 제품 약 1/3 의 노무비가 조용히 0 이 된다. 터지지 않고 틀리는 종류다.

해결: `eval` 을 쓰지 않고 숫자 리터럴만 받는 재귀하강 파서로 푼다. 식별자가 하나라도 나오면
(`=T6*U$3`, `=SUM(A1:A3)`) 거부한다. 설계서 §5.1 의 "JavaScript `eval` 로 파일의 수식을
실행하지 않는다" 를 지킨다.

→ **새 원본을 읽는 계획을 쓸 때마다 "그 열의 수식 셀이 어떤 형태인지" 를 먼저 조사하는 단계를 넣는다.**
   수식 셀의 존재만 확인하고 형태를 안 보면 같은 함정에 다시 빠진다.

### B열 머리글은 브랜드가 아니다

`classifyRow` 가 `brand` 로 분류하는 행의 실제 값 289종을 보니 `DP to HDMI 케이블&젠더`,
`Jumper Cord`, `후렉시블`, `비디오 스위처` 같은 **품목 묶음 이름**이었다. 일부에만 제조사가
섞여 있고(`야마하_Digital Mixer_DM/CL 이상`) 규칙이 없다.

`ProductVariant.brand` 에 넣으면 화면이 "브랜드: DP to HDMI 케이블&젠더" 라고 거짓말한다.
→ `options.group` 에 원문을 남기고 `brand` 는 `''` 로 둔다. **추측하지 않는다.**
→ 브랜드가 정말 필요하면 별도 입력이 필요하다 (O10).

### 감사 패턴에서 `매입` 단독 매칭을 뺀다

건축에서 `매입` 은 **매립형 설치**를 뜻한다. 품셈 코드에
`7-11-5_Speaker-고정_30W 이하_해설②매입⑩천장설치` 처럼 정상적으로 나온다.
`매입처|매입단가|매입가격|매입원가|구매처|구입처|원가표` 로 좁힌다.

### 숨김 시트 2개 제외는 옳았다

`LED전광판 계산`(88행)은 제품 목록이 아니라 **계산 시트**다
(`000인치 삼성 LED전광판 (0x0)`, `LED 설치 (00.00㎡)` — 자리표시자).
LED 전광판은 고르는 게 아니라 구성하는 것이고, 그 일은 `svt-led-calculator` 가 한다.
`단종, 미사용 제품`(67행)은 이름 그대로다.
