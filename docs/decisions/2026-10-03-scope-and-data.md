## D2 — 가격 두 종류의 취급

설계서는 "원가"를 한 덩어리로 다뤘다. 실제로는 두 가지이고 취급이 다르다.

| | 매입가 | 판매단가 |
|---|---|---|
| 어디 | 사용자가 그때그때 올리는 **별도 원가표** | 품셈 파일 **G열** 1,442개 |
| 고객이 보나 | 아니오 | **예** — 견적서에 찍혀 나감 |
| 저장소 | ⛔ 절대 금지 | ✅ 허용 (D3) |
| 처리 | 메모리 전용 `PrivateCostSession`, 새로고침 시 소멸 | 배포 데이터 |

매입가 취급은 설계서 §8 그대로이며 변경 없다.

## D3 — 판매단가 공개: 허용. 단 파일은 분리한다

**결정: 전 품목 판매가표가 배포 산출물에 포함돼도 좋다.**

사용자 판단 근거: 판매가는 어차피 고객 견적서에 찍혀 나간다.
감수하는 위험: 전 품목 가격표가 **한꺼번에** 노출되면 경쟁사가 통째로 가져갈 수 있다.
사용자가 이 위험을 인지하고 선택했다.

### 단, 되돌릴 수 있게 만든다

```
data/approved/products.json   제품명·규격·단위·분류·브랜드·품셈코드   (1,468)
data/approved/prices.json     판매단가만                              (1,442)
```

**처음부터 두 파일로 나눈다.** 현재는 둘 다 배포한다.

나중에 "판매가는 가리자"로 바뀌면 → `prices.json` 을 배포에서 빼기만 하면 된다. 코드 수정 없음.
그때 앱은 단가를 `미등록` 으로 표시하고, 사용자가 품셈 파일을 올리면 채운다 (매입가와 같은 통로).

이 전환이 공짜인 이유: 설계서 §5.6 이 이미 "가격 미등록을 0원으로 처리하지 말고 확정을 차단하라"고
요구하므로, **가격 없는 상태는 어차피 구현해야 하는 정상 경로**다.

→ 한 파일에 섞지 말 것. 섞으면 이 선택이 비가역이 된다.

## D4 — 부자재 자동 추천: 1차 범위에서 제외

**결정: 설계서 §7 의 연결 그래프 기반 자동 추천을 1차에 넣지 않는다.**

이유:

1. 포트 데이터가 **어느 파일에도 없다.** 평택 견적서는 완성된 견적서지 장비 사양서가 아니고,
   품셈 파일은 가격·품셈표다. 장비별 단자 구성은 제조사 사양서를 모델마다 수작업 입력해야 나온다.
2. 설계서 §0 이 정의한 "웹 완성"은 *"다운로드 후 Excel 후편집 불필요"* 이지 *"케이블 자동 선택"* 이 아니다.
   사용자가 케이블을 직접 넣어도 그 조건은 충족된다.
3. 설계서 §7 자체가 "검증된 근거 없이 자동 확정하지 말라"를 반복 경고한다. 포트 데이터 없이
   만들면 **틀린 추천을 자신 있게 하는** 결과물이 된다.

영향: 설계서 §11 단계 5 전체, 인수기준 A05 가 1차 범위 밖으로 이동한다.

### 이미 만들어진 코드의 처분 (2026-10-03 추가)

D4 가 정해지기 **전에** 구현 세션이 단계 5 를 이미 만들었다
(`src/domain/accessories/{types,evaluate,allocate}.ts`, 테스트 24개 통과).
지우지 않고 다음과 같이 둔다.

| 모듈 | 상태 | 이유 |
|---|---|---|
| `allocate.ts` | **보존·재사용 예정** | 배정 원장·멱등성·중복 배정 방지는 요구량이 어디서 나오든 같다. D5 의 딸림 항목 표가 요구량을 만들면 그 뒤 로직이 이것이다 |
| `evaluate.ts` | **비활성(inert)** | 포트 그래프를 입력으로 받는데 포트 데이터가 없다. 호출되지 않는다 |
| `types.ts` | 보존 | 위 둘의 타입 |

인수기준 **A05 는 1차 범위 밖**이며 완료로 보고하지 않는다. 저장소에 코드가 있다는 사실이
기능이 동작한다는 뜻이 아니다 — 설계서 §13-9("구현 계획에 나열된 기능을 완료 사실로 보고하지 않는다")의 적용이다.

## D5 — 대신: 사용자가 작성하는 "연동 항목 표" (설계 합의, 작성 보류)

사용자 제안:

> 특정 제품과 연동해야 하는 항목을 서로가 이해할 수 있는 폼으로 만들어서 서로 정보를 전달한다.
> 예를 들어 UTP 전송기면 UTP 케이블이 반드시 필요한 조건을 내가 거기다 기입한다.

프로그램이 사양서에서 **추측**하지 않는다. 사용자가 **선언**하고 프로그램은 따른다.

### 사용자 답변 — 현재 요약 (2026-10-05)

#### 사용자가 **말한 것만** 적는다

```
10-04  "어떤 장비에 어떤 부자재가 반드시 따라옵니까"  →  = UTP전송기들
10-05  "UTP 전송기 외에 연동 부자재가 더 있습니까"    →  = 2m HDMI 케이블
10-05  hdbaset 전송기 알티컴 ct104 경우 pc의 hdmi출력을 tx연결
       lan으로 rx연결. rx출력 hdmi케이블로 tv연결
10-05  ctr100은 hdbaset3.0 4k60전송기도 마찬가지
10-05  ctr100은 tx모드 rx모드 선택해서 사용하기 때문에 그래
```

#### 확정된 사실

```
PC ──HDMI──▶ TX ──LAN(UTP)──▶ RX ──HDMI──▶ TV
```

| | |
|---|---|
| 관계 | 2m HDMI 는 **HDBaseT 전송 장비에 딸린다.** 별개 사례가 아니다 |
| 위치 | **한 구간의 양 끝에 하나씩** — PC↔TX, RX↔TV |
| `XDM-CTR100` | **TX 모드 / RX 모드를 골라 쓰는 제품.** 1대가 한쪽 끝이다 |
| **세는 단위** | **전송 장비 1대당 2m HDMI 1개.** 사용자 확인 2026-10-05: *"전송기당 hdmi가 1개씩 붙는게 맞는거지"* |

따라서 규칙은 품목 종류로 갈리지 않고 **대수**로만 정해진다.

```
전송 장비 1대            ->  2m HDMI 1개
한 구간 (TX 1 + RX 1)    ->  2m HDMI 2개 + UTP 케이블 1개
```

#### ⛔ 내가 적었던 "송수신기 = HDMI 2개" 는 틀렸다

`XDM-CTR100` 이 품셈에 `HDBT 송수신기` 로 등록돼 있길래 **TX+RX 한 묶음**으로 읽고
HDMI 2개라고 적었다. 사용자가 *"ctr100은 tx모드 rx모드 선택해서 사용하기 때문"* 이라고
알려 줬다. **모드 선택형이라 1대가 한쪽 끝이고, HDMI 는 1개다.**

→ `송수신기` 라는 품명이 두 가지를 뜻한다.

```
모드 선택형 1대    XDM-CTR100      한쪽 끝.  HDMI 1
TX+RX 한 묶음      ?               양 끝.    HDMI 2
```

**품명만으로 갈리지 않는다.** 앞서 *"규칙이 품명으로 결정된다"* 고 적은 것을 철회한다.
대신 **대수로 센다.** 품명이 `송신기` 든 `수신기` 든 `송수신기` 든, 장비 1대에 HDMI 1개다.
남는 문제는 **한 품목 줄이 장비 몇 대를 뜻하는지**뿐이다.

#### `SET` 단위 품목 — 사용자 확인 (2026-10-05)

세 품목 모두 사용자 답변을 받았다. **셋 다 단위가 `SET` 인데 뜻이 서로 달랐다.**

| SKU | 모델 | 품셈 품명 | 단위 | 실제 | 2m HDMI |
|---|---|---|---|---|---:|
| `VID-0269` | `VE801` | HDBT 송수신기 | `SET` | **송신기 1 + 수신기 1, 2대 묶음** | **2개** + UTP 1 |
| `VID-0270` | `VE801-T` | HDBT 송신기 | `SET` | **송신기 1대** | **1개** |
| (없음) | `PV185S` | HDBT 송수신기 | `SET` | **쓰지 않는다. 전부 삭제** | 해당 없음 |

> 사용자 원문 (2026-10-05)
> - `VE801` → "송신기·수신기 2대 묶음" (선택지 2-A)
> - `VE801-T` → *"VE801-T는 송신기야"*
> - `PV185S` → *"PV185S는 전부 삭제 사용하지 않을거야"*

#### ⚠ `SET` 이라는 단위는 대수를 알려 주지 않는다

`VE801` 과 `VE801-T` 는 **단위가 똑같이 `SET` 인데 하나는 2대이고 하나는 1대다.**
단위 문자열로 대수를 추정하면 `VE801-T` 에서 HDMI 가 2배가 된다.

→ **대수는 SKU 별로 사람이 지정한다.** 단위로도, 품명으로도, 접두사로도 추정하지 않는다.
→ 품명은 참고가 된다 (`송수신기` 2대 / `송신기` 1대). 다만 `XDM-CTR100` 도 품명이
  `HDBT 송수신기` 인데 1대이므로, **품명만으로 결정하지는 않는다.**

#### `PV185S` — 확인한 것

승인 카탈로그 `data/approved/products.json` 에 **처음부터 없다** (검색 0건).
품셈 원자료에는 있으나 `[단종, 미사용 /HDBaseT 송수신기_기]` 묶음에 들어 있어
추출 단계에서 이미 걸러졌다. **따로 지울 코드나 데이터가 없다.**
사용자 지시는 이 상태를 유지하라는 뜻으로 기록한다.

#### 아직 모르는 것

| | |
|---|---|
| `CT-` / `CR-` 접두사 | **전체를 TX/RX 로 단정하지 않는다.** CTR100 이 반례를 보였다 |
| 그 외 장비의 연동 항목 | 받지 못했다 |

→ **확인된 SKU 에만 역할을 붙인다.** 접두사 규칙으로 일반화하지 않는다.

#### 구현으로 넘기기 전에 정할 것

자동으로 HDMI 를 붙이려면 아래가 먼저 필요하다. **Task 5 에 섞지 않는다.**

```
구성도 BOM 에 이미 HDMI 가 있을 때 중복 처리
세트 품목과 개별 품목이 섞였을 때 중복 처리
"2m HDMI 케이블" 이 어느 SKU 인지 고르는 계약
```

#### 표 자체는 미작성이다

HDBaseT 계열 하나가 정리됐을 뿐이다. 열린 항목 **O9** 유지.

---

### (이력) 1·2차 답변 당시의 해석 — 현행 아님

아래는 3~5차 답변 전의 중간 결론이다. **지금은 위 요약을 따른다.**

- 2차 답변 직후: *"UTP 전송기에 딸린 것인가, 별개 사례인가"* 로 양쪽 열어 두었다 → **딸린 것으로 확정됨**
- 3차 답변 직후: *"송신기 1 · 수신기 1 · 송수신기 2"* 로 정리했다 → **송수신기 2 는 철회됨**
- 당시 붙였던 HDBaseT 일반 지식 설명은 담당자 해석이었고 사용자 확인을 받지 않았다

| **예** | **아니오** | **자동 추가 + 수량 칸 비워 경고 표시 → 안 채우면 견적 확정 차단** |

사용자가 `기존 공급` / `별도 공사` / `견적 범위 제외` 사유를 적으면 통과한다 (설계서 §7.5).

사용자가 수량을 고치거나 삭제하면 프로그램이 다시 늘리지 않는다 (설계서 §7.3).

### 상태: **보류**

사용자 지시: *"특정 제품과 연동돼서 필요한 것들은 나중에 정리하는 걸로 해서 꼭 나한테 질문을 해 줘."*

사용자 확인:

### 규칙

```
한쪽 슬롯 수 = 프레임 채널 수 ÷ 4
```

카드 1장 = 4포트(품셈 파일 외 사양 자료에 "슬롯당 포트 4" 명시).

| 프레임 | 채널 | 입력 슬롯 | 출력 슬롯 |
|---|---:|---:|---:|
| XDM-12 | 12×12 | **3** | **3** |
| XDM-20 | 20×20 | 5 | 5 |
| XDM-36 | 36×36 | 9 | 9 |
| XDM-72 | 72×72 | 18 | 18 |
| XDM-144 | 144×144 | 36 | 36 |
| XDM-216 | 216×216 | 54 | 54 |

**사용자가 표 전체를 확인했다 (2026-10-04).** 유도값이 아니다.

> 만약 입력이 20개 출력이 20개면 XDM-20 을 써야지.

즉 **필요한 입출력 수가 프레임을 정한다.** 역방향으로도 쓸 수 있다 — 구성도의 연결 수를 세면
맞는 프레임을 제안할 수 있다.

품셈 파일에는 **XDM-12 / 20 / 36 세 종만** 있다(VID-0138 / 0137 / 0136). 72 이상은 당장 쓰이지 않는다.

### 왜 필요한가 — 실물 구성도가 실제로 틀려 있었다

사용자가 준 실물 구성도(`av-diagram-1791037942542.json`)가 **XDM-12 에 카드 8장**
(입력 4 + 출력 4)을 꽂고 있다. 양쪽 1장씩 초과다.

사용자 확인: **"구성도가 틀린 거야."**

카드 1장이 74만~286만원이다. 프레임에 안 들어가는 구성으로 견적이 나가면 **현장에서야 안다.**

### ⚠ 이것이 흔드는 전제

D7 은 사용자의 이 판단 위에 서 있다:

> 아이템을 선정해 하는 방식은 실수할 확률이 높다. 구성도를 그려 놓고 거기 맞는 장비와 케이블을
> 산출하는 게 가장 정확하다.

그 판단은 여전히 옳다 — **옮겨 적는 단계가 사라지기 때문**이다. 다만 **구성도 자체도 틀릴 수 있다**는
것이 실물로 확인됐다. 따라서 변환기는 구성도를 **무조건 믿지 않는다.** 검사할 수 있는 것은 검사한다.

이것이 `ProductPicker` 를 되살릴 이유는 아니다. 구성도의 오류는 **기계가 잡을 수 있고**
(프레임 용량, 포트 초과, 연결 없는 장비), 사람이 옮겨 적다 생기는 누락은 잡을 수 없다.

### ⚠ 슬롯을 덜 채우는 것은 정상이다 — 블랭크로 메워 출고된다

사용자 확인 (2026-10-04):

> XDM-12 쓰더라도 **8×8 구성해서 사용**도. 견적서에는 없는 **블랭크 슬롯을 껴서 출고**되거든.

| | |
|---|---|
| 카드 수 < 슬롯 수 | **정상.** 남는 슬롯은 블랭크 패널로 메워 출고된다 |
| 블랭크 슬롯 | **견적서에 넣지 않는다.** 출고 시 끼워 나가는 것이지 견적 품목이 아니다 |
| 카드 수 > 슬롯 수 | **오류.** 물리적으로 안 들어간다 |

→ 변환기는 **빈 슬롯을 채우려 들지 않는다.** 블랭크 행을 생성하지 않는다.

### 처리 — 방향이 중요하다. 셋을 구분한다

사용자 확인 (2026-10-04):

> XDM-12 프레임을 썼는데 입력이 만약에 20개일 수는 없는 거지. **그때는 프레임을 바꿔야 되는 거지.**

연결 수는 **상한이 아니라 하한**이다. 카드보다 적으면 여유고, 많으면 오류다.

| # | 조건 | 뜻 | 판정 |
|---|---|---|---|
| A | 카드 포트 > 프레임 채널 | 카드가 물리적으로 안 들어감 | **blocking** |
| B | 연결 수 > 카드 포트 | **카드가 부족.** 꽂을 자리가 없음 | **blocking** |
| C | 연결 수 > 프레임 채널 | 카드를 늘려도 프레임이 못 받음 → **프레임 교체** | **blocking** |
| — | 카드 포트 > 연결 수 | 여유. 8×8 로 쓰려고 덜 꽂는 것도 정상 | **검사하지 않음** |

마지막 줄이 D10 의 앞선 판단이었고 그대로 유지한다. **덜 꽂는 것은 정상**이며
남는 슬롯은 블랭크로 메워 출고된다(견적서에 넣지 않는다).

C 는 A·B 의 상위 원인이다. 셋을 따로 세우는 이유는 **사용자에게 할 일이 다르기 때문**이다 —
A·B 는 카드만 조정하면 되는 경우가 있고, C 는 프레임을 바꿔야 한다.

### 필요 채널과 프레임 제안

```
필요 채널 = max(장착 카드 포트 수, 실제 연결 수)
적정 프레임 = 필요 채널 이상을 받는 가장 작은 프레임
```

예시:

```
매트릭스 구성

  프레임        XDM-12   (12채널 · 한쪽 3슬롯)
  장착 카드      입력 4장 = 16포트 · 출력 4장 = 16포트    ⚠ A: 슬롯 3장까지
  실제 연결      입력 3 · 출력 1

  필요 채널      16  (카드 쪽이 더 큼)
  적정 프레임     XDM-20

  [ XDM-20 으로 ]   [ 카드를 3장으로 줄이기 ]
```

```
프레임        XDM-12   (12채널)
  장착 카드      입력 2장 = 8포트
  실제 연결      입력 20                 ⚠ B: 카드 부족 · C: 프레임 초과

  필요 채널      20  (연결 쪽이 더 큼)
  적정 프레임     XDM-20 + 입력 5장
```

### 이 검사는 옵션 카드 정의 없이도 된다

카드가 입력인지 출력인지는 포트 id 에 이미 있다 — `…-456-0-xlsxopt-456-in-1`,
`…-454-0-xlsxopt-454-out-1`. 노드의 `inputs`/`outputs` 배열로도 갈린다.
**O15(av-builder 옵션 export)를 기다리지 않아도 구현할 수 있다.**

열린 항목 O17 → 계획 `2026-10-04-diagram-to-quote.md` **Task 7**.

## D13 (2026-10-04) — 품셈 파일 두 판본은 같은 데이터의 두 가지 보기다

### 하반기판에서 G·H·N 세 열을 빼면 상반기판과 정확히 같아진다

실측 대조 — 한 칸도 어긋나지 않는다.

| 하반기 261002 | 3열 제거 후 | 상반기 260408 |
|---|---|---|
| G·H **원가**(단가/금액) | — | (없음) |
| I·J 재료비 | → G·H | G·H 재료비 |
| K·L 노무비 | → I·J | I·J 노무비 |
| M 합계 | → K | K 합계 |
| N **재료비 이윤** `(I/G)-1` | — | (없음) |
| O 비고 | → L | L 비고 |
| P 제조사/구매처 | → M | M 제조사/구매처 |
| Q 영업비고 | → N | N 영업비고 |
| R 노무비(메모) | → O | O 노무비(메모) |
| S 품셈코드 | → P | P 품셈코드 |
| T·U·V 요율·할증·표준단가 | → Q·R·S | Q·R·S |
| W~ 직종별 | → T~ | T~ 직종별 |

```
하반기판 = 사내 원본   (원가 G·H + 이윤 N 포함)
상반기판 = 제출용 사본  (그 3열을 뺀 것)
```

버전 차이가 아니라 **용도 차이**다. 추출기는 **두 레이아웃을 모두 읽을 수 있어야** 한다.
판별은 2행 머리글로 한다 — `G2 == '원가'` 면 하반기 레이아웃.

### ☠ 배율이 수식에 적혀 있다 — 판매가만으로 원가가 역산된다

하반기판 I열(판매단가) 1,587건 중 **1,068건이 수식**이다.

```
I6 = ROUNDUP(G6 * 1.4, -3)
                  ↑ 배율이 그대로 보인다
```

배율 분포: 1.1(273) · 1.3(223) · 1.2(183) · 1.4(109) · 1.5(103) · 1.15(26) · 1.35(21) · 1.25(20) · 1.05(15)

**`원가 = 판매가 ÷ 배율`.** 배율을 함께 내보내면 원가를 지운 의미가 없다.

→ **추출기는 값만 읽고 수식은 버린다.** 이미 그렇게 돼 있다(`cell_text` 가 `=` 로 시작하면 `None`).
   하반기 레이아웃으로 바꿀 때 이 규칙을 깨뜨리지 않는다.

### 사용자의 실제 운영 방식 — 이미 보안상 정확하다

> 보통 제출 시에는 **G·H열은 삭제**해서 고객사에 견적을 보내고, 우리는 G·H열에 원가 포함되는 거는
> 우리만 보관해서 원가분석을 해.
>
> 실제 견적 나갈 때는 **배율을 전부 없애고 숫자로** 나가.

끊어야 할 고리가 셋인데 셋 다 끊고 있다.

| 고리 | 조치 |
|---|---|
| 원가 값 | G·H 열 삭제 |
| 이윤율 | N 열 삭제 |
| **배율 수식** | **숫자로 치환** ← 셋 중 가장 놓치기 쉽다 |

**실물 검증 완료.** 평택·DSR 견적서 ZIP 전수 문자열 검사:

```
배율·ROUNDUP   0건      원가·매입·구매처   0건      이윤·마진   0건
```

단가는 전부 숫자 상수다. 남은 수식 9개는 `=INT(G17*20%)` 등 배관·잡자재 계산이며 원가와 무관하다.

### ⚠ 사용자에게 알린 것 — 「케이블 및 커넥터」 시트만 G열 숨김이 풀려 있다

```
LED전광판 계산      숨김: G, N, T~
단종, 미사용 제품    숨김: G, N, T~
케이블 및 커넥터     숨김:    N, T~     ← G 빠짐
오디오             숨김: G, N, T~
```

받은 파일은 원가가 비어 있어 문제없으나, **사내 원본도 그렇다면** 그 시트는 원가가 보이는 채로 돈다.

## D19 (2026-10-04) — 가이드 세부내역의 파생 행 두 개 (구현 세션 실측)

가이드 `세부내역` 의 품목 영역은 **전부 품목이 아니다.** 아래 두 줄이 예약돼 있다.

```
6~12   실제 품목
13     배관 기타자재   = 바로 윗 배관 행의 판매금액 × 40%
14     잡자재비        = (13 포함한 위 금액) × 2%
15     직접비계
```

### 새 기계를 만들지 않는다

`CustomerDerivedRow` 에 `derived: DerivedBasis` · `rate: DecimalText` 가 **이미 있고**
계산 엔진이 처리한다. 두 줄은 새 개념이 아니라 **기존 파생 행 두 개**다.

### 40% 는 D12 와 일치한다. 2% 는 새 값이다

| 값 | 출처 |
|---|---|
| 배관 기타자재 **40%** | `간접비_DS` · `간접비_SDC, SDI` 시트 · 가이드 G13 — 셋 다 40% |
| 잡자재비 **2%** | **가이드 세부내역 14행 (이번에 처음 측정)** |

40% 는 D12 의 보류 상태 그대로다 — 평택만 20% 였고 사용자가 *"어떤 배관을 쓰느냐에 따라
결정된다. 나중에 알려 줄게"* 라고 했다. **기본 40% + 입력값**(O21).

### ⚠ 배관 기타자재의 원가측은 **프로파일마다 다르다** (2026-10-04 정정)

처음에는 *"13행은 원가 칸이 공란"* 이라고 적었다. 그때는 **일반 `_원` 한 장만** 있었다.
DS 원가본을 확보한 뒤 두 장을 나란히 재니 **다르다.**

수식 원문 실측(금액은 읽지 않았다):

| 행 | | 일반 `_원` | DS `_원` |
|---|---|---|---|
| 13 배관 기타자재 | **원가 단가 G13** | **(공란)** | **`=H12*40%`** |
| | 판매 단가 I13 | `=J12*40%` | `=J12*40%` |
| 14 잡자재비 | 원가 단가 G14 | `=INT(SUM(H6:H13)*2%)` | 같음 |
| | 판매 단가 I14 | `=INT(SUM(J6:J13)*2%)` | 같음 |

읽는 법: `H12` 는 **직전 배관 행의 원가 금액**, `J12` 는 **직전 배관 행의 판매 금액**이다.
즉 양쪽 모두 *"직전 배관 행의 금액 × 40%"* 라는 같은 모양이고, **일반만 원가측을 비워 둔다.**

잡자재비는 두 프로파일이 완전히 같고, `6행부터 13행까지` 를 합산하므로
**배관 기타자재를 포함한다.** 따라서 배관 기타자재가 잡자재비보다 **먼저** 와야 한다.

> ⚠ 커밋 `2bf24a4` 의 메시지에 *"잡자재비가 먼저"* 라고 적혀 있는데 **반대다.**
> 코드와 시험은 `배관 기타자재 → 잡자재비` 로 맞게 되어 있다. 메시지만 틀렸다.

**일반이 원가측을 비워 두는 것은 템플릿 자체의 설계**이지 미등록(§5.6)이 아니다.
생성기가 이것을 "원가를 모른다"로 바꿔 읽으면 안 된다.

의도된 비대칭이다. 그런데 두 군데서 **거짓 실패**를 만든다:

1. **원가 ↔ 판매 대사** — *"모든 행이 원가 × 배율 = 판매"* 를 기대하면 13 에서 깨진다
2. **원가 유출 검사** — 13 의 판매금액이 무관한 제품의 원가와 우연히 일치할 수 있다.
   이미 두 건 겪었다. 파생값은 특히 잘 걸린다

→ **제외하는 것은 딱 두 가지뿐이다.** 넓게 빼면 파생비가 검증 사각지대가 된다.

| | 파생 행에 |
|---|---|
| `원가 × 공통 배율 = 판매` 대사 | **제외** — 13 은 원가가 없다. 공통 배율이 성립하지 않는다 |
| 출처 없는 **숫자 일치**만으로 하는 누출 판정 | **제외** — 파생값은 무관한 원가와 잘 겹친다 |
| 파생비 자체의 엔진 ↔ Excel 금액 검증 | **유지** — 40%·2% 가 맞게 계산됐는지는 반드시 본다 |
| 구조 검사 · sentinel 검사 | **유지** — 필드 출처로 판정하므로 숫자 우연과 무관하다 |

*"파생 행은 대조에서 뺀다"* 로 뭉뚱그리면 **배관 기타자재 금액이 틀려도 아무도 모른다.**
빼는 것은 **공통 배율 전제**와 **출처 없는 숫자 일치** 둘뿐이고, 그 이유를 테스트에 글자로 남긴다.

### ✅ 잡자재비 — 사용자 확정 (2026-10-04). O27 닫힘

> 잡자재비는 **LED캐비넷 제외** 모든 계 금액에 **× 2%** 적용 기준이야

```
잡자재비 = INT( (LED 캐비넷을 뺀 모든 품목의 금액 합) × 2% )
```

**모든 견적에 붙는다.** 자동 생성 여부에 대한 답이기도 하다.

#### 실제 견적 네 건에서 그대로 확인된다 — 가이드 수식에는 없던 조건이다

| 시트 | 디스플레이 | 잡자재비 수식 |
|---|---|---|
| **1-1** | 스크린 + 프로젝터 (**LED 없음**) | `=INT(SUM(J5:J40)*2%)` ← **첫 품목부터** |
| **1-2** | 174인치 IFR P1.5 (**LED**) | `=INT(SUM(J11:J52)*2%)` ← **11행부터** |
| 1-3 | 163인치 MMF P1.5 | `=INT(SUM(J11:J53)*2%)` |
| 2-2 · 3-2 | LED | `J11` 부터 |
| 2-3 | LED | `J12` 부터 |

LED 가 없는 1-1 은 `J5`(첫 품목)부터 더하고, LED 가 있는 시트는 **캐비넷 블록을 건너뛴다.**

시트 1-2 의 경계:

```

```

**캐비넷만 빠지고 부속품은 들어간다.** S-BOX·자석지그·설치프레임킷은 포함된다.

> ⚠ 가이드 템플릿의 `=INT(SUM(H6:H13)*2%)` 는 **LED 가 없는 경우**의 모양이다.
> 그 수식을 그대로 쓰면 LED 견적에서 **캐비넷까지 더해 잡자재비가 부풀어 오른다.**
> 캐비넷은 견적에서 가장 비싼 품목이라 오차가 크다.

**캐비넷 계열 묶음에 속한 품목을 합산에서 뺀다.** 품명으로 추측하지 않는다.

사용자 확인:

> **IEA 단종, IEA-E 모델 변경 · IFR 단종, IFR-M 모델 변경**

세대 교체 관계라는 뜻이다. 같은 제품군이므로 **전부 캐비넷**이다.

그리고 품셈 실측에서 **`The Wall` 은 별도 제품군이 아니라 브랜드 이름**임이 드러났다.

```
삼성 The Wall MPF P0.84     LH008MPFAAA/WC
삼성 The Wall MMF P0.94     LH009MMFRGS/XU
삼성 The Wall MMF-S P1.25   LH012MMFYGS/XU
```

`The Wall` 묶음 머리글은 그 아래 `MPF`·`MMF`·`MMF-S` 를 묶는 **상위 이름**이다.
앞서 `The Wall` 을 별도 캐비넷 계열로 센 것은 내 오독이었다.

**「LED전광판 계산」 시트의 캐비넷 묶음 — 아홉 개가 전부다.**

```
IEA 계열       IEA · IEA-F · IEA-E · IEA-EF
IFR 계열       IFR-M · IFR-MF
The Wall 계열   MPF · MMF · MMF-S
```

나머지 묶음(`S-BOX 및 부속품` · `설치프레임킷_*` · `데코프레임_*` · `케이블 자재` ·
`지빅` · `S/FTP Cable` · `OM3 Optical Cable` · `HDMI Cable` · `배관`)은 **부속품이라 합산에 포함**된다.

##### ⚠ 품셈 자료의 불일치 — 단종 처리가 한쪽만 됐다

사용자는 `IEA` 와 `IFR` 을 **둘 다 단종**이라고 했다. 그런데 품셈 파일은 다르다.

| 모델 | 사용자 | 품셈 파일에서의 자리 |
|---|---|---|
| IFR | 단종 | **「단종, 미사용 제품」** ✅ 맞게 옮겨짐 |
| **IEA** | **단종** | **「LED전광판 계산」(현행)** ⛔ 아직 남아 있음 |

##### 사용자 지시 (2026-10-05)

> **IEA는 단종. IEA 후속 모델은 그대로 있게**

```
단종으로 옮길 것   삼성 IEA P1.5 · P2.0 · P2.5   (LH015/020/025 IEACLS/KR) 세 줄
현행에 남길 것     IEA-E · IEA-EF   (후속 모델)
```

**`IEA-F` 는 언급되지 않았다.** 품셈에서 이미 갈려 있다 — `IEA-F P1.5`·`P2.0` 은 단종 시트에,
`IEA-F P2.5` 는 현행에 있다. **건드리지 않는다.**

→ **품셈 파일을 고치는 것은 사용자다.** 프로그램이 임의로 단종 처리하지 않는다(D1).
   세 줄이 옮겨지면 카탈로그 재추출 때 자동으로 반영된다.

```
[IEA] 삼성 IEA P1.5   LH015IEACLS/KR     ← 현행 시트
[IEA] 삼성 IEA P2.0   LH020IEACLS/KR
[IEA] 삼성 IEA P2.5   LH025IEACLS/KR
```

D22 3항에 따라 **품셈 목록에 있는 자재만 쓴다.** 그러면 단종된 IEA 가 현행 시트에 있으므로
**새 견적에서 고를 수 있게 된다.** 사용자에게 알려 판단을 받아야 한다.

→ **프로그램이 임의로 단종 처리하지 않는다.** 품셈 파일이 진실의 출처다(D1).
   사용자가 품셈에서 옮기면 자동으로 사라진다.

#### 원본에 손상이 있다

시트 1-2 의 `A53 = '=#REF!+1'` 이다. 번호 열의 참조가 끊겨 있다.
**사례 자료를 읽을 때 이런 것이 나온다**(D21). 읽기 실패로 처리하지 말고 건너뛴다.

### (닫히기 전 조사 기록) 잡자재비 자동 생성 근거 — 사용자 결정이 없었다

Codex 가 *"D19 의 템플릿 사실만으로 전 시스템 자동 적용을 추정하지 않겠다"* 며 근거를 물었다.
대화 기록 전체를 뒤졌다.

```
사용자가 잡자재비를 언급한 발언    0건
```

`잡자재|2%|기타자재` 로 검색해 나온 15건이 **전부 Codex 중계 메시지**다. 사용자 본인 발언은 없다.
**자동 생성은 추론이다.** 그 점을 분명히 한다.

#### 다만 뒷받침하는 실물 자료가 셋이다

| 출처 | 내용 |
|---|---|
| 가이드 템플릿 | 세부내역 14행에 존재. `=INT(SUM(…)*2%)` |
| **품셈 파일** | **`간접비_DS`·`간접비_SDC, SDI` 두 시트**에 `잡자재비 / 자재비의 2% / 식` |
| **실제 사례 36시트** | **36/36 전부에 존재.** 없는 시트 0개 |

세 출처가 서로 독립적이다. D5(연동 항목)에서 경계한 *"같이 나온다고 규칙은 아니다"* 와는
성격이 다르다 — 그쪽은 **동시 등장 통계**뿐이고, 이쪽은 **품셈에 정의가 적혀 있다.**

#### ★ 새로 드러난 사실 — 잡자재비는 **간접비 시트**에 정의돼 있다

제품 시트가 아니라 `간접비_DS` · `간접비_SDC, SDI` 에 있다. 규격 칸이 `자재비의 2%` 이고
단위가 `식` 이다.

```
정의된 자리   간접비 시트 (두 프로파일 모두)
쓰이는 자리   견적서 세부내역 14행 (직접비 영역)
```

##### ⚠ 여기서부터는 **가설이다. 확정이 아니다**

*"간접비 시트에 적혀 있으니 간접비 프로파일에 딸린 것"* 은 **자리만 보고 세운 추측**이다.
시트에 함께 있다는 것이 소속을 증명하지 않는다. 배관 기타자재 비율(`후렉시블 20%, CD관 40%`)도
같은 시트에 적혀 있지만 **배관 종류가 정하는 값이지 프로파일 값이 아니다**(D12·D22).
같은 자리에 있어도 성격이 다를 수 있다.

```
사실    잡자재비가 간접비_DS · 간접비_SDC, SDI 두 시트에 `자재비의 2%` 로 적혀 있다
가설    따라서 간접비 프로파일에 딸린 항목이다        ← 확인 안 됨
```

가설이 맞다면 DS·일반을 바꿀 때 잡자재비도 따라와야 하고, 파생 행 하나로만 다루면 그 연결이
끊긴다. **두 프로파일 값이 똑같이 2% 라 지금은 어느 쪽이든 결과가 같다** — 그래서 지금
확인할 방법이 없고, 한쪽이 바뀌는 날에야 드러난다.

→ **가설로 남기고 구현하지 않는다.** 사용자에게 물을 때 함께 확인한다.

#### 처리

- **자동 생성을 지금 구현하지 않는다.** 근거는 강하지만 사용자 결정이 아니다
- 사용자에게 물을 때는 **두 가지를 함께** 묻는다 —
  ① 모든 견적에 자동으로 붙는가 ② 간접비 프로파일에 딸린 것인가
- O25(트레이 비율)와 **섞지 않는다.** 별개 질문이다

열린 항목 **O27**.

### 품목 행은 항상 모자란다

가이드의 7줄은 예시 분량이다. 평택 147줄 · DSR 206줄이다.
**행 삽입이 예외가 아니라 기본**이고, 13·14·15 이하가 따라 내려가면서
직접비계 SUM 범위 · 간접비 기준 참조 · 갑지 `=세부내역!M25` 가 전부 같이 움직여야 한다.

## D22 (2026-10-04) — 배관 품목·비율·자재 범위 (O24·O21·O11 닫힘)

사용자 지시 세 건이다. 전부 **품셈 파일 실측으로 뒷받침**된다.

### 1. 무엇이 배관인가 (O24)

사용자 확인:

> 난연CD/합성수지 Conduit ← 배관 · Flexible Conduit SF-28 ← 배관 · **케이블 트레이 ← 배관**

품명에 `Conduit` 이 없는 **케이블 트레이도 배관**이다. → **이름으로 추측하면 안 된다.**

#### 품셈 파일에 실재하는 배관 품목 (실측)

```
「케이블 및 커넥터」  묶음: 배관자재 > 후렉시블
  Flexible Conduit (고장력,방수)     16㎜_GW-16 · 22㎜_GW-22 · 28㎜_GW-28
  Flexible Conduit (고장력,비방수)   16㎜_SF-16 · 22㎜_SF-22 · 28㎜_SF-28 · 36㎜_SF-36

「전원, 랙, 판넬, 몰드 및 보양」  묶음: 케이블 트레이
  케이블 트레이   100mm x 100mm   (3M 기준, 단위 EA)
```

#### 판정 방식 — 품명이 아니라 **묶음 이름**으로 한다

품셈 파일의 B열 묶음 머리글이 이미 분류를 해 두었다(`배관자재` · `케이블 트레이`).
**그 묶음에 속한 품목이 배관이다.** 품명 문자열 검사(`Conduit` 포함 등)를 쓰지 않는다.

→ 카탈로그 추출 때 `options.group` 에 원문 묶음 이름이 들어간다(`buildProducts.ts`).
   그 값으로 판정한다. 새 배관 품목이 품셈에 추가돼도 묶음만 맞으면 자동으로 따라온다.

### 2. 기타자재 비율 (O21 닫힘)

**추측값이 아니다.** 품셈 파일 `배관 기타자재` 행의 설명 칸에 **글자로 적혀 있다.**

```
후렉시블 20%,  CD관 40%
```

| 배관 종류 | 기타자재 비율 |
|---|---:|
| 후렉시블 (Flexible Conduit 전 규격) | **20%** |
| CD관 | **40%** |
| **케이블 트레이** | **30%** ← 사용자 지정 (2026-10-05) |

#### ✅ 케이블 트레이 30% — 사용자 확정 (O25 닫힘)

```
후렉시블      20%    품셈 설명 칸에 적혀 있음
CD관          40%    품셈 설명 칸에 적혀 있음
케이블 트레이   30%    품셈에 없음. 사용자가 알려 준 값
```

⚠ **셋 중 트레이만 품셈에 근거가 없다.** 사용자 구술이 유일한 출처다.
`30%` 를 코드에 박지 말고 **다른 둘과 같은 자리에서 관리**한다 — 품셈에 트레이 행이
추가되면 그쪽을 따르고, 없으면 이 값을 기본값으로 쓴다. 출처를 화면에 표시한다.

#### (닫히기 전 기록) 비율이 비어 있던 이유

위 1항에서 **트레이를 배관으로 분류**했다. 그런데 품셈 설명 칸은 **후렉시블과 CD관 둘만**
말한다. 트레이는 둘 중 어느 쪽도 아니다.

```
후렉시블  20%     품셈에 적혀 있음
CD관      40%     품셈에 적혀 있음
트레이     ?       아무 데도 없음
```

트레이가 배관 분류라는 이유로 **기본값 20% 를 자동 적용하면 안 된다.** 다른 물건이다.
트레이는 단위도 다르다(`EA`, 3M 기준) — 후렉시블은 `10M` 다.

→ 트레이에 기타자재 행을 붙일지, 붙인다면 몇 %인지 **사용자에게 물어야 한다.**
   그때까지는 **확인 필요**로 둔다. 0% 로도 20% 로도 처리하지 않는다.

> 이 구멍은 Codex 가 화면 계획을 쓰다 찾았다. 1항(트레이도 배관)과 2항(후렉시블/CD관 두 종류)을
> 따로 적어 두니 **그 사이가 비는 것이 안 보였다.** 분류와 비율을 같은 표에서 다뤄야 했다.

D12 에서 *"평택 20% vs 가이드 40%"* 로 갈렸던 것이 이것으로 설명된다 —
**다른 값이 아니라 배관 종류가 달랐다.** 평택은 후렉시블, 가이드는 CD관이다.

기본값을 하나로 박지 않는다. **배관 품목에 따라 고른다.** 사용자가 공간별로 바꿀 수 있는 것은 그대로다.

### 3. 자재 범위 (O11 닫힘)

> **원가삭제 표준품셈 목록 자재만 사용하면 되**

→ **카탈로그를 보충하지 않는다.** 품셈에 없으면 견적에 넣지 않는다.

O11 의 105건(평택 18 + av-builder 미매칭 87)은 **추가 대상이 아니다.**
av-builder 쪽 장비를 품셈 목록에 맞추는 작업은 사용자가 따로 진행 중이다.

→ 미등록 품목이 구성도에서 들어오면 **경고를 세우고 사람이 처리**한다. 임의로 만들지 않는다.

### ⚠ 남은 모순 둘 — 사용자 확인 필요

**(가) 난연CD/합성수지 Conduit — 선택지는 만들되 품목이 아직 없다**

사용자 지시:

> **CD관, 후렉시블 둘 다 집어넣고 내가 선택해서 쓸 수 있게 하는데 기본은 후렉시블이 기본이야**

```
배관 종류 선택   ○ 후렉시블  (기본) → 기타자재 20%
                ○ CD관             → 기타자재 40%
```

가이드 실측이 이 대응을 한 번 더 확인해 준다.

```
가이드 12행   난연CD/합성수지 Conduit   28㎜, 천정   10M
가이드 13행   배관 기타자재             배관자재40%        ← CD관이라 40%
```

#### ⚠ 그런데 CD관 **제품 행이 품셈 파일에 없다**

전 시트를 뒤졌다. `전선관 몰드 AL/PVC` 는 몰드지 CD관이 아니다.

```
품셈에 있는 배관   후렉시블 7종 + 케이블 트레이 1종
품셈에 없는 것     난연CD/합성수지 Conduit
```

*"품셈 목록 자재만 사용"*(위 3항)을 지키면 **CD관을 고를 수는 있어도 넣을 품목이 없다.**

→ 처리: **선택 기능은 지금 만든다.** CD관을 골랐는데 품셈에 품목이 없으면
   *"품셈에 CD관 품목이 없습니다"* 로 **차단하고 알린다.** 0원으로 넘기거나
   후렉시블로 몰래 바꾸지 않는다.

→ 사용자가 품셈 파일에 **한 줄 추가**하면 바로 쓸 수 있다. 가이드 기준 필요한 값:

```
묶음    「케이블 및 커넥터」 > 배관자재 > (CD관)
품명    난연CD/합성수지 Conduit
규격    28㎜, 천정   (다른 굵기가 있으면 함께)
단위    10M
```

이것은 **데이터 추가**지 코드 변경이 아니다. 품셈만 갱신하면 선택지가 살아난다.

**(나) 판매 묶음 단위 — 맞추지 않아도 된다 (2026-10-04 닫힘)**

사용자 답:

> 굳이 꼭 판매 단위를 맞춰 가지고, 예를 들어 **20m가 필요한데 판매 단위가 30m니까 30m 넣을
> 필요는 없어.** 가급적이면 맞추면 좋지만 **반드시 그럴 필요는 없어.**

→ **D8 규칙 1 의 `10M 단위 올림` 을 그대로 쓴다.** 50M·30M 묶음으로 **강제 올림하지 않는다.**

```
20m 필요  →  수량 2 (10M × 2)        ← 이렇게 한다
             수량 3 (30M 묶음에 맞춤)  ← 하지 않는다
```

설명 칸의 `50M 단위 판매` · `30M 단위 판매` 는 **구매 담당이 참고할 정보**이지
견적 수량을 정하는 규칙이 아니다. 화면에 보여 주되 수량을 바꾸지 않는다.

아래는 닫히기 전의 기록이다.




## D18 (2026-10-04) — 출력 3종과 파일명 (최종)

|---|:---:|:---:|:---:|:---:|:---:|:---:|

### ⚠ 1단계에 제조사/구매처가 남는다 — 추론으로 뒤집지 말 것

사용자가 **열 단위로 직접** 지정했다:

> **1) 원가 삭제시 (영업팀외 직원공유용) — G,H,N열 삭제**
> 3) 원가+설명+표준품셈 삭제시(사실상 고객전달용) — G,H,N열 + D열 + **P~BE열 삭제**

1) 에 P 가 없다. 1단계는 **영업팀 외 사내 직원**용이므로 구매처가 보여도 된다는 판단이다.
설계서 §8.1 의 "매입처는 고객에게 나가면 안 된다"는 **2단계**에 걸리는 규칙이지
1단계에 걸리는 규칙이 아니다.

D16 이 이것을 X 로 적었다가 정정했다. **같은 실수를 반복하지 않도록 여기 표를 기준으로 한다.**

### AI 메모는 "지운다"가 아니라 "안 쓴다"

사용자가 두 번 말하면서 열 주소가 한 칸 어긋났다 — *"**BF**열에 너의 의견을 적어줘"* 와
*"AI가 기록하는 부분은 **BE**는 3가지 경우 모두 삭제해"*.

열 주소를 규칙으로 삼으면 *"BF 에 쓰고 BE 를 지운다"* 가 되어 **메모가 고객 파일에 남는다.**

→ **0단계에서만 쓴다. 1·2단계는 애초에 쓰지 않는다.** 지우는 단계를 두지 않는다.
   `src/export/customer/projection.ts` 의 allowlist 원칙과 같다.
   (0단계 위치는 BF 고정. 단 **17직종 전제**이고 CMS 21직종이면 직종 블록 안이다.)

### ⚠ "누적"은 담기는 정보의 관계이지, 구현 방식이 아니다

위 표는 **포함 정보가 단계마다 줄어든다**는 뜻이다. 단계가 올라갈수록 더 빼기만 한다.

**그런데 이것 자체는 안전 보증이 아니다.** 앞서 *"거꾸로 가는 경우가 없어 원가가 나갈 길이 없다"*
고 적었는데 틀렸다 — 순서가 안전을 만드는 게 아니라 **구현이 만든다.**

```
✅ 출력마다 allowlist 로 독립 생성한다.      1·2단계 함수는 원가를 인자로 받지 못한다
⛔ 0단계 파일을 만들어 열을 지워 1·2를 만든다.  지우다 빠뜨리면 그대로 나간다
```

`src/export/customer/projection.ts` 가 이미 이 방식이다 — *"문서에서 뺄 것을 지우는 방식이
아니라, 넣을 것을 하나씩 적는 방식"*. 같은 원칙을 세 단계 전부에 적용한다.

**원가가 채워진 파일을 지워서 재사용하는 경로를 코드에 두지 않는다.**

- 파일명: `견적서_{현장명}_{YYMMDD}{꼬리표}.xlsx`. 현장명은 사용자가 입력한다
- **꼬리표가 붙으면 사내용. 고객에게는 꼬리표 없는 것만**
- AI 변환 메모는 **0단계에만**. 공유하는 순간부터 뺀다
- 기본 선택은 **2단계**. 아무것도 안 고르면 가장 안전한 것이 나간다
- `_원` 을 고르면 경고를 띄우고 한 번 더 확인받는다

## D16 (2026-10-04) — 출력물의 열 배치 (시연 피드백)

사용자가 실물 산출물 3장을 열어 확인한 뒤 준 지시다.

### 잘 돼 있다고 확인된 것

> 열 너비·테두리·글꼴 / 인쇄 미리보기에서 한 장에 들어가는지 / 간접비 9항목이 제자리에 있는지
> — **이 부분은 잘되어 있어.**

O1(원본과 인쇄 서식 1:1 시각 대조)의 상당 부분이 사람 눈으로 확인됐다.

### ⛔ 고칠 것 1 — K열(비 고)에 프로그램 메모가 들어가 있다

생성물 실측:

```
K5 = "구성도 — 모델 'LH98QMCEBGCXKR'…"
K6 = "구성도 — 카탈로그 미등록. 확인 필요"
K7 = "구성도"
```

**K는 「비 고」 열이고 인쇄 영역 안이다.** 고객이 보는 자리에 *"구성도에서 왔다"* 같은
**프로그램 사정**을 적었다.

사용자 지시:

> 현재 K열에 뭔가 설명되어 있는데 이 부분은 **인쇄영역 오른쪽에** 들어갔으면 해.

→ 변환 메모·출처·경고는 **인쇄 영역 밖 열**로 옮긴다. 비고 열은 **사람이 적는 칸**으로 비워 둔다.

#### 자리 — 비고와 제조사/구매처 사이에 열을 하나 끼운다 (사용자 제안)

> 비고와 제조사/구매처 사이에 열 추가해서 너의 의견을 넣어주면 어때?

```
┌─ 인쇄 영역 ──────────────────────────┐
 A번호 B품명 C규격 D설명 E단위 F수량
 G·H재료비  I·J노무비  K합계  L비고
└─────────────────────────────────┘
   M  [변환 메모]      ← 새 열. 인쇄되지 않는다
   N  제조사/구매처
   O  영업비고
   P  노무비 메모
   Q  품셈코드   R 요율   S 할증   T 표준단가
   U~ 직종별 품·금액 … 건축목공
```

비고 **바로 다음 칸**이라 화면에서 한 칸만 오른쪽으로 가면 보인다. 행과 나란히 붙는다.

들어갈 내용 — **견적서 받는 사람이 아니라 작성자가 보는 것**:

```
구성도에서 옴 — 노드 3개 합산
카탈로그 미등록 — 확인 필요
카탈로그에 2건 걸림 (CTL-0051, CTL-0053)
옵션 카드 정의 없음 — 수량만 살림
배관: 공간 1개 × 50m
```

#### ⚠ 열을 켜고 끄면 뒤쪽이 밀린다

`설명`(D)과 `제조사/구매처`가 출력 종류에 따라 빠진다(D14). 그러면 그 뒤 열 주소가 전부 바뀐다.

| 출력 | 설명 | 매입처 | 품셈 영역 시작 |
|---|---|---|---|
| 고객 제출용 (설명 끔) | — | — | 비고 다음다음 |
| 사내 공유용 | O | — | 한 칸 뒤 |
| 원가 분석용 | O | O | 두 칸 뒤 + 원가 2열 |

→ **열 주소를 코드에 박지 않는다.** 행 주소를 품목 수에 따라 계산하듯, 열도 **선택된 구성에서
   계산**한다. exporter 가 이미 행에 대해 그렇게 하고 있으므로 같은 방식을 열에 적용한다.

→ 그래서 "원본과 똑같은 열 자리"는 **포기한다.** 출력 종류가 셋인 이상 한 자리에 고정할 수 없다.
   대신 **머리글 이름이 자리를 알려준다** — 사람은 `제조사/구매처` 라는 글자를 찾지 N열을 찾지 않는다.

### ⛔ 고칠 것 2 — 인쇄 영역 밖 데이터가 통째로 빠졌다

```
우리 생성물   dim = A1:K22    인쇄 A1:K22     ← K 에서 끝
평택 원본     dim = A1:BA40   인쇄 A1:K35     ← 인쇄는 K 까지, 데이터는 BA 까지
```

원본은 인쇄 영역 **오른쪽에 품셈 계산 영역이 살아 있다.** 우리 생성물엔 없다.

사용자 지시:

> **제조사/구매처부터 건축목공 금액까지 인쇄영역 밖 자료도 그대로 유지**되어야 해.

유지할 범위 (상반기 레이아웃 기준):

| 열 | 내용 |
|---|---|
| M | 제조사/구매처 |
| N | 영업비고 |
| O | 노무비(확인 메모) |
| P | 품셈 코드 |
| Q·R·S | 품목별 요율 · 할증 · 표준단가 |
| T~BA | 직종별 품·금액 (… 건축목공까지) |

이것이 있어야 **노무 단가가 어떻게 나왔는지 Excel 안에서 역추적**할 수 있다.
지금은 노무비가 숫자로만 찍혀 근거를 볼 수 없다.

### ⚠ 그런데 M·N 은 매입처 정보다 — 출력 종류에 따라 갈린다

`제조사/구매처`(M)·`영업비고`(N)는 **고객용에 나가면 안 된다**(설계서 §8.1).

실제 누출로 잡혔다.

→ **D14 의 출력 종류와 묶어서 처리한다.**

## D14 (2026-10-04) — 출력 열 선택

사용자 지시:

> **D열**은 우리 직원(원가를 볼 필요 없는)끼리만 확인하는 용도야. 그래서 D열은 유지할 수도 있고
> 지울 수도 있어야 해. **원가 G·H열도 마찬가지로 지울지 여부를 선택**할 수 있으면 좋겠어.

### 두 열의 위험도가 다르다. 같은 방식으로 다루지 않는다

| 열 | 내용 | 기본값 | 켤 때 |
|---|---|---|---|
| **D** 설명 | 사내 공유용 메모. **원가와 무관** | 끔 | 체크 한 번 |
| **G·H** 원가 | 매입가 | **끔** | **명시적 행동 + 파일명 표시** |
| **N** 이윤 | `(I/G)-1` | **끔** | **G·H 와 함께만** |

**N 은 G·H 에 종속된다.** 원가 없이 이윤만 내보내면 `판매가 ÷ (1+이윤)` 으로 원가가 복원된다.
G·H 를 끄면 N 도 강제로 꺼진다. 사용자가 따로 켤 수 없다.

### 출력 세 종류

```
① 고객 제출용     D 선택 · 원가 없음 · 숫자 상수만
② 사내 공유용     D 켬    · 원가 없음          ← 사용자가 말한 "원가를 볼 필요 없는 직원"
③ 원가 분석용     D 선택 · 원가 있음 · 파일명에 표시
```

②가 ①과 다른 점은 D열 하나뿐이다. ③만 민감하다.

### 안전장치

- **열을 숨기지 않는다. 아예 만들지 않는다.** 숨긴 열은 엑셀에서 끌어내면 보인다
  (설계서 §8.7 "열만 숨겨 고객용으로 보내지 않는다")
- ③은 파일명에 **`내부용_원가포함`** 을 넣는다 (설계서 §8.7)
- ③은 일반 저장 버튼으로 자동 저장하지 않는다
- 세 종류 모두 **ZIP 전수 검사**를 통과해야 내려간다. ①②는 원가 문자열 0 이 조건
- 기본값은 **①**. 사용자가 고르지 않으면 가장 안전한 것이 나간다

## D12 (2026-10-04) — 간접비 프로파일 두 가지 (O7 닫힘)

사용자 지시:

> 간접비 요율은 **삼성전자 DS 쪽 간접비**가 다르고, 그 이후에 **일반적인 공사 간접비**가
> 별도로 있어. 그래서 간접비는 총 **두 가지를 선택**할 수 있어야 해.

### ⚠ 요율만 다른 게 아니다 — 항목 수·이름·기준이 전부 다르다

품셈 파일 두 시트를 실측했다.

#### 프로파일 A — `간접비_DS` (9항목)

| # | 항목 | 기준 | 요율 | 기본 |
|---|---|---|---:|---|
| 1 | 간접노무비 | 노무비 대비 | 0.0486 | 적용 |
| 2 | 고용보험료 | 노무비 대비 | 0.00424 | 적용 |
| 3 | 산재보험료 | 노무비 대비 | 0.00961 | 적용 |
| 4 | 연금보험료 | 노무비 대비 | 0.01215 | **미적용** — 1개월 이상 공사 限 |
| 5 | 건강보험료 | 노무비 대비 | 0.00957 | **미적용** — 1개월 이상 공사 限 |
| 6 | 노인장기요양보험료 | 노무비 대비 | 0.00124 | **미적용** — 1개월 이상 공사 限 |
| 7 | 산업안전보건관리비 | 직접비 대비 | 0.0311 | 적용 |
| 8 | 퇴직공제부금비 | 노무비 대비 | 0.00621 | **미적용** — 1억원 이상 공사 限 |
| 9 | 공과잡비 | 직접비 + 간접노무비 + 산업안전관리비 | 0.1 | 적용 |

#### 프로파일 B — `간접비_SDC, SDI` (7항목)

| # | 항목 | 기준 | 요율 | 기본 |
|---|---|---|---:|---|
| 1 | **일반관리비** | 직접비 대비 | 0.06 | 적용 |
| 2 | 산업안전보건관리비 | 직접비 대비 | 0.0207 | 적용 |
| 3 | **산재 및 고용보험료** | 노무비 대비 | 0.0457 | 적용 |
| 4 | 퇴직공제부금 | 노무비 대비 | 0.023 | **미적용** — 1억원 이상 |
| 5 | 국민연금보험료 | 노무비 대비 | 0.045 | **미적용** — 1개월 이상 |
| 6 | 국민건강보험료 | 노무비 대비 | 0.03545 | **미적용** — 1개월 이상 |
| 7 | 노인장기요양보험료 | **건강보험료 대비** | 0.1295 | **미적용** — 1개월 이상 |

### 세 가지가 구조적으로 다르다

1. **항목 수** 9 vs 7
2. **항목 구성** — A 의 `간접노무비` ↔ B 의 `일반관리비`. A 는 고용·산재가 분리, B 는 `산재 및 고용보험료` 로 통합. **B 에는 공과잡비가 없다.**
3. **기준(basis) 종류가 늘어난다** — B 의 노인장기요양은 **`건강보험료 대비`** 다.
   기존 `IndirectBasis` 에 없던 축이다. **다른 간접비 항목을 기준으로 삼는 경우**를 받아야 한다.

→ 앞서 적은 *"프로파일은 `IndirectCostRule[]` 을 통째로 갈아끼우는 것"* 이 맞다.
   요율만 바꾸는 구조였으면 B 를 표현할 수 없었다.

### 미적용 조건이 데이터에 있다

비고 열에 조건이 적혀 있다.

```
1개월 이상 공사 限   연금·건강·노인장기요양
1억원 이상 공사 限   퇴직공제부금
```

**자동으로 켜지 않는다.** 공사 기간과 금액은 견적 단계에서 확정되지 않는다.
조건을 `IndirectCostRule` 에 문구로 싣고 사용자가 켜게 한다.

### 두 샘플 견적서 모두 프로파일 A 를 썼다

DSR·평택 둘 다 9항목 구조다. 적용되는 6개 요율이 `간접비_DS` 와 **완전히 일치**한다
(고용 0.00424 · 산재 0.00961 · 산업안전 0.0311 · 퇴직 0.00621 · 공과잡비 0.1).

미적용 3개만 소수점 아래가 다르다(연금 0.01215 vs DSR 0.01283 등). **금액이 0 이라 영향은 없다.**
프로젝트마다 요율 표기가 조금씩 갱신된 것으로 보인다.

### 화면 표기 — 확정 (2026-10-04)

사용자 확인: *"삼성전자DS 또는 일반 이렇게 표기하면 될듯."*

| 품셈 시트 | 화면 표기 | 항목 |
|---|---|---|
| `간접비_DS` | **삼성전자DS** | 9 |
| `간접비_SDC, SDI` | **일반** | 7 |

시트 이름(`SDC, SDI`)을 화면에 쓰지 않는다. 계열사 약어라 읽는 사람이 범위를 오해한다 —
SDC·SDI 전용이 아니라 **삼성전자 DS 외 전부**에 쓰는 것이다.

프로파일 id 는 `ds` / `general` 로 둔다. 표기 문자열과 분리해 나중에 이름만 바꿀 수 있게 한다.

### 기본 선택은 **삼성전자DS** — 사용자 지시 (2026-10-04)

> **간접비 기본은 DS로 선택되게 해 주고**

새 견적의 기본 프로파일은 `ds` 다. 근거가 있다 — **DSR·평택 두 샘플 견적서가 모두 9항목 구조**이고
적용되는 6개 요율이 `간접비_DS` 와 완전히 일치한다(위 참조). 실제로 쓰는 쪽이 DS 다.

사용자가 공간(시스템)마다 바꿀 수 있는 것은 그대로다. 기본값만 정한 것이다.

### 요율은 **% 로 표기한다** — 사용자 지시 + 원본과 일치

> **요율은 %로 표기해 줘**

**원본 가이드가 이미 그렇게 하고 있다.** 실측:

```
F17 = 0.0486    서식 `0.000%`   →  4.860%
F18 = 0.00424   서식 `0.000%`   →  0.424%
F25 = 0.1       서식 `0.000%`   →  10.000%
```

→ 화면도 **같은 서식 `0.000%`** 를 쓴다. D17(원본을 따른다)과 어긋나지 않는다.

#### ⚠ 소수점 **셋째 자리**를 반드시 지킨다

```
0.00424  →  0.424%     셋째 자리까지. 원본과 같다
         →  0.42%      둘째 자리로 줄이면 원본과 달라진다
         →  0.4%       첫째 자리면 거의 0 으로 보인다
```

요율이 `0.00124`(노인장기요양) 처럼 작은 값이 있어서 **자리를 줄이면 서로 다른 항목이
같은 숫자로 보인다.** 사용자가 원본 견적서와 화면을 나란히 놓고 대조할 때 안 맞는다.

**저장은 지금처럼 소수(`DecimalText`)로 하고 표시만 % 로 바꾼다.** 입력도 % 로 받는다면
`4.86` 을 `0.0486` 으로 되돌리는 변환이 양방향으로 정확해야 한다 — 부동소수로 하지 않는다.

### ⏸ 배관 기타자재 비율 — 보류 (O21)

| 출처 | 비율 |
|---|---:|
| `간접비_DS` · `간접비_SDC, SDI` 시트 | **40%** |
| SDC·SDI 견적서 가이드 `세부내역` G13 | **40%** |
| 평택 LED 시트 | **20%** |

사용자 확인 (2026-10-04):

> 이거는 **어떤 배관을 쓰느냐에 따라서 결정**이 돼. 그 부분은 나중에 알려 줄게. 나도 지금 헷갈려.

→ **프로파일(DS/일반)에 딸린 값이 아니다.** 배관 종류가 정한다.

처리:

- 값을 **상수로 박지 않는다.** `배관 기타자재 = 배관자재 금액 × 비율` 의 비율을 **입력값**으로 둔다
- 기본값 **40%** (세 군데 중 두 군데, 그리고 최신 가이드가 그렇다)
- 사용자가 공간별로 바꿀 수 있게 하고, **바꾼 값을 보여준다**
- 배관 종류 ↔ 비율 대응표는 사용자가 알려줄 때 추가한다

**추측해서 20%/40% 를 자동으로 고르지 않는다.** 사용자도 아직 정리가 안 된 상태다.

| 필요한 것 | 상태 |

## D7 보강 (2026-10-04) — 입구가 둘이다. 구성도와 직접 선택

사용자 지시:

> 아주 간단한 견적은 — 예를 들어 PC 하고 프로젝터 설치. PC, 프로젝터, 그 사이를 연결하는
> HDBaseT 전송기 또는 HDMI 케이블만 필요한데, 이런 견적은 그냥 이 견적서 구성기에서도

> 그냥 선택해서 간접비가 붙어서 최종 견적서 폼으로 나오는 거지.

### D7 원안과 모순이 아니다

품목 선택 경로가 새로 만들 것은 **행을 만드는 부분뿐**이다.

→ 구현 지침: `toQuote.ts` 를 **"구성도 전용" 으로 짜지 않는다.**
   `행 목록 + 머리정보 → QuoteDocument` 를 공용 함수로 두고, 구성도 변환은 그 앞단에서
   행을 만들어 넘기는 구조로 한다. 품목 선택도 같은 함수를 쓴다.

## D8 (2026-10-04) — 케이블·커넥터·배관 산출 규칙

사용자가 준 규칙이며, 실제 견적서(DSR·평택)로 검산했다.

### 1. 케이블 길이 보정

```
총 산출거리 = (도면 직각 경로 + 상하 높이) × 1.3
```

- **직각 경로**: 비스듬히 재지 않는다. 가로 + 세로로 꺾어서 잰다. 케이블이 실제로 그렇게 간다.
- **상하 높이**: 랙에서 천장으로 입상, 장비 앞에서 입하. 도면에 없으므로 **천장고를 입력받는다.**
- `× 1.3`: 우회·여유.

산출 후 처리:

| 케이블 종류 | 처리 |
|---|---|
| 완제품 (`ready-made`) | **길이 계단으로 올림** → `1 · 2 · 3 · 5 · 7 · 10 · 15 · 20m`. 수량은 개수(EA) |
| 벌크 (`manufactured`) | 길이 합산 후 **10M 단위 올림** |

길이 계단은 DSR·평택 견적서에서 실제로 쓰인 값이다(UMC-001/002/003, CBL-H300-050/070, AHOC-010/015).

### 2. 커넥터

```
구간당 3개 (사용 2 + 예비 1)  →  10EA 묶음 단위로 올림
```

**검산 통과.** 실제 견적서에서 역산한 구간 수가 깔끔하게 떨어진다.

| 시트 | 커넥터 | 역산 구간 |
|---|---:|---|
| 평택 LED Display | 10개 | 3.3 |
| 평택 월컨트롤 | 20개 | 6.7 |
| 평택 랙·배관배선 | 10개 | 3.3 |
| DSR 접견실 | 30개 | 10.0 |

### 3. 배관 — ⚠ 60% 규칙은 폐기한다

사용자 확인:

> 배관은 A→B 경로에 케이블 보호하는 용도라서 **1개 회의실당 50m면 충분**하다.

**"총 거리 × 60%" 는 쓰지 않는다.** 실측에서 10%~61% 로 흩어졌고, 그 이유가 설명된다 —
배관은 케이블 총량이 아니라 **보호가 필요한 경로**에 걸리는 것이라 케이블 길이와 비례하지 않는다.

> ### ⛔ 아래 50m 규칙은 **폐기됐다.** 바로 아래 "2026-10-04 보강"을 따를 것
>
> 윗부분만 읽고 `공간당 50m` 를 구현하지 않도록 여기서 막는다.
> D16 에서 같은 실수를 한 적이 있다 — 정정문 **위에 남은 옛 표**를 그대로 구현할 뻔했다.

~~배관 = 공간(시스템) 1개당 50m → Flexible Conduit 10M 단위 × 5~~
~~사용자가 공간별로 조정할 수 있게 하되 기본값 50m 로 둔다.~~ ← **폐기**

#### 2026-10-04 보강 — 50m 고정이 아니라 **거리 × 줄 수**로 받는다

사용자가 실제 산정 방식을 설명했다.

> 배관은 우리가 **얼추 예측**하는 건데 **다소 많은 측면**이 있어. 예를 들어 10×7m 공간에
> 7m 쪽 벽면에 장비실과 디스플레이가 서로 마주본다면 10m 배관을 해야 해.
> 그 경우 **왕복 3줄**은 쓴다고 가정하면 될 것 같아.
>
> (입력 방식) **장비실과 가장 먼 장비 거리를 기입**하는 거지.

```
배관 길이 = (장비실 → 가장 먼 장비까지의 거리) × 줄 수
```

| 입력 | 기본값 |
|---|---|
| 장비실에서 가장 먼 장비까지의 거리 (m) | 없음. 사용자가 넣는다 |
| 줄 수 | **3** |

**가장 먼 거리**를 쓰므로 가까운 장비까지 과하게 잡힌다. 그것이 *"다소 많은 측면이 있다"* 의
뜻이며 **의도된 여유**다. 평균 거리로 바꾸어 "정확하게" 만들지 않는다.

##### "왕복"은 ×2 가 아니다 — 사용자 확정 (2026-10-04)

처음 표현이 *"왕복 3줄"* 이라 두 가지로 읽혔다. 두 배 차이라 직접 확인했다.

> `10 m × 3줄 = 30 m` **이게 맞아**

```
확정   배관 = 거리 × 줄 수            10m × 3 = 30m
아님   배관 = 거리 × 2 × 줄 수        10m × 2 × 3 = 60m
```

→ **프로그램은 ×2 를 하지 않는다.** `거리 × 줄 수` 만 한다.
→ 계산 결과를 **화면에 그대로 보여 준다** (`10m × 3줄 = 30m`).

곱하는 수를 사용자가 직접 넣고 결과가 보이므로, 현장이 다르면 줄 수로 조정한다.
**숨겨진 배수를 두지 않는 것이 핵심이다.** 몰래 두 배 하고 안 보여 주는 쪽이 위험하다.

##### 구성도에는 거리가 없다

av-builder 가 주는 것은 **선을 그린 그림**이고 실제 거리는 없다(`docs/interface/av-builder.md`).
UI 좌표를 미터로 환산하지 않는다. **공간별로 사람이 입력한다.**
화면 계획 Task 3 의 `SpaceInput` 이 이 값을 받는다.

### 4. 이 규칙들이 만드는 행

| 행 | 근거 |
|---|---|
| 케이블 (완제품/벌크) | 구성도 선 + 길이 |
| `- Pass Through RJ45 Connector` 등 | 규칙 2 |

## D3 보강 (2026-10-04) — 판매단가를 공개하지 않는다

D3 은 "공개 정적 사이트라 어쩔 수 없다"는 전제에서 나온 선택이었다. **그 전제가 사라졌다.**

사용자가 **AV Portal 에 이메일 인증을 걸기로** 했고(D6 참조), 도메인도 이미 확보돼 있다.
따라서 `prices.json` 을 **인증 뒤에 두면 전 품목 가격표가 공개되지 않는다.**

| | D3 원안 | D3 보강 |
|---|---|---|
| 판매단가 | 공개 감수 | **인증 뒤. 공개하지 않음** |
| 파일 분리 | 유지 | **유지** — 이 구조 덕에 코드를 고치지 않는다 |
| 사용자 작업 | 원가표 1개 업로드 | **그대로** |

→ 구현 변경 없음. `products.json` / `prices.json` 분리를 그대로 두고 **배포 위치만** 인증 뒤로 간다.
   D3 이 요구한 "되돌릴 수 있게"가 실제로 값을 했다.

## D6 — 배포: 영업팀 도메인 + 이메일 인증 + 서브도메인 분리 (2026-10-04 확정)

사용자 결정:

> AV 포털은 특정 사용자만 **이메일 인증**받아서 사용할 수 있게 한다.
> 도메인은 **메인 페이지용 / 영업팀 전용 2개**가 이미 있다.

### 배치

```
메인 도메인 (공개)              회사 소개 등 — 이 프로젝트 범위 밖

영업팀 도메인 (전원 인증)
  ├─ sales.<회사>.com           AV Portal (메뉴·진입점)
  ├─ builder.sales.<회사>.com   av-builder (구성도)
  └─ cpq.sales.<회사>.com       AV-CPQ (견적)   ★ 별도 origin
```

### 근거

- **서브도메인은 별도 origin 이다.** `cpq.sales…` 의 localStorage·IndexedDB·메모리를
  `sales…` 의 스크립트가 읽을 수 없다. 설계서 §8.5 가 요구한 원가 격리가
  **도메인 추가 구매 없이** 성립한다.
- ⚠ 어제 적은 "같은 origin 의 다른 경로는 분리가 아니다"는 **경로**(`/cpq/`) 이야기다.
  **서브도메인**(`cpq.`)은 다르다. 이 구분을 혼동하지 말 것.
- 인증은 **주소별로** 건다. 셋 다 같은 이메일 목록을 쓰면서도 서로 격리된다.
- AV-CPQ 는 `connect-src 'none'` CSP 로 배포해야 하는데(설계서 §8.5),
  한 사이트에 두 가지 보안 정책을 걸 수 없으므로 **분리가 필수**다.

### GitHub Pages 는 쓸 수 없다

정적 파일만 내주는 곳이라 **접근 제어 기능이 없다.** 저장소를 private 로 해도 배포 사이트는
공개다. 사이트 접근 제어는 GitHub Enterprise Cloud 기능이며 일반 계정에 없다.

호스팅을 옮겨야 한다. **앱 코드 변경은 불필요하다** — 정적 사이트 앞에 인증을 세우는
방식(예: Cloudflare Pages + Access 의 이메일 일회용 PIN)이면 지금 만든 것이 그대로 올라간다.
구체적 제품·요금 조건은 착수 시 확인한다. 이 문서는 제품을 확정하지 않는다.

### 합치지 않는다

`av-builder` 와 AV Portal 을 **코드로 합치지 않는다.** 메뉴 링크로 묶는다.

- 배포 주기가 다르다. builder 는 장비·포트 추가로 자주 바뀌고 포털은 거의 안 바뀐다.
  묶으면 한쪽 빌드 실패가 다른 쪽 배포를 막는다.
- 합쳐서 얻는 것이 "주소 하나"인데 그것은 링크로도 된다.
- 사용자가 느끼는 "하나"는 설계서 §1 대로 **같은 디자인**에서 온다. 코드 통합이 아니다.

AV-CPQ 는 위 격리 근거로 **합칠 수 없다.**

### D6 보강 (2026-10-04) — 사용 인원 6명. 전부 무료 구간이다

사용자 확인:

> 우리 회사 직원 중에 이것을 쓸 사람은 **6명** 정도

#### ★ 저장소 잠금과 사이트 인증은 **다른 문제**다

사용자가 *"유료 계정으로 바꾸면서 private 으로"* 를 고려했다. **그럴 필요가 없다.**

```
GitHub 무료 계정
  private 저장소     무제한 무료      ← 이미 된다
  GitHub Pages      public 에서만
```

**GitHub 를 유료로 올려도 배포 사이트는 여전히 공개다.** 사이트 접근 제어는 Enterprise 기능이다.
즉 결제해도 2번 문제(영업팀만 접근)가 안 풀린다.

→ **사이트를 Cloudflare 로 옮기면 GitHub Pages 가 필요 없어지고, 그 순간 저장소를
   무료로 private 으로 돌릴 수 있다.** 결제할 이유가 사라진다.

#### 비용 (6명 기준)

| | |
|---|---|
| Cloudflare Pages 호스팅 | 무료 |
| Cloudflare Access 이메일 OTP | 무료 (무료 구간 인원 한도 한참 아래) |
| GitHub private 저장소 | 무료 |
| 도메인 | 보유 중 |

6명은 Netlify·Vercel·Azure Static Web Apps 어디를 써도 무료 구간이다.
**인원이 제약이 아니므로 기능으로 고르면 된다.**

Cloudflare 를 권하는 이유는 요금이 아니라 **서브도메인별 정책**과 **CSP 헤더 직접 설정**이다.
후자는 `connect-src 'none'`(설계서 §8.5) 때문에 필수인데 GitHub Pages 에서는 안 된다.

회사가 Microsoft 365 를 쓴다면 Azure Static Web Apps 도 후보다 — 직원 계정을 그대로 쓴다.
**사용자에게 확인하지 않았다.**

#### 순서 — 마지막에 잠근다

```
1  화면 완성
2  사용자 PC 에서 확인
3  도메인 네임서버를 Cloudflare 로 · 사이트 배포 · 이메일 6개 등록
4  저장소를 private 으로        ← 여기서 잠가야 잃는 것이 없다
```

3번 전에 저장소를 잠그면 Pages 가 꺼진다. **순서가 중요하다.**

#### 현재 상태 (2026-10-04)

```
저장소   PUBLIC · main 49커밋 푸시됨 · 기본 브랜치 main
공개된 것  평택 26파일 · DSR 6 · 삼성전자 5 · 실제 노임 5 · PC 경로 3
안 들어간 것  원가(매입가) 0 · 작성자 실명 0
```

사용자가 *"일단은 그냥 오픈 공개로"* 를 선택했다. 위험은 설명했고 사용자 판단이다.
**과거 커밋에도 현장명이 남으므로**, 나중에 파일만 고쳐도 기록에서는 지워지지 않는다.
가명 치환을 원하면 별도 작업이다.

### 남은 확인

- 회사가 Microsoft 365 / Google Workspace 를 쓰는지 (쓰면 Azure 후보가 올라간다)
- 서브도메인 DNS 설정과 인증 적용은 단계 8
- 요금·무료 한도는 **착수 시점에 다시 확인한다.** 자주 바뀐다
