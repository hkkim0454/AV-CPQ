# 세션 분담과 통합 절차

**작성:** 2026-10-05 · 계획 세션
**지시:** 사용자 — *"codex와 claude code 각자 작업을 하되 최종은 claude code 병합하게 계획을 해줘"*

---

## 0. 먼저 — 같은 폴더를 쓴다는 제약

세 세션 모두 **작업 폴더가 같다.**

```
b09d2119  계획        claude-opus-5     C:\…\AV-CPQ
344060a1  Codex       gpt-6-astra       C:\…\AV-CPQ   ← 같다
d2a784d1  Claude Code claude-sonnet-5   C:\…\AV-CPQ   ← 같다
```

여기서 따라오는 것이 둘 있다.

**첫째, 같은 파일을 동시에 고칠 수 없다.** 한쪽이 쓴 내용을 다른 쪽이 덮어쓴다.
Git 브랜치로도 해결되지 않는다. 브랜치는 여럿이어도 **작업 트리는 하나**라서,
한쪽이 브랜치를 바꾸면 다른 쪽의 작업 중인 파일이 통째로 바뀐다.

**둘째, 그래서 `git merge` 로 합칠 것이 생기지 않는다.** 모두 같은 트리에 커밋한다.

→ 여기서 말하는 **"병합"은 Git 병합이 아니라 "작업 결과를 합쳐 전체가 맞는지 확인하는 일"**로
   정의한다. 그 일을 **Claude Code 가 맡는다.**

### 진짜 동시 작업을 원한다면

`git worktree` 로 폴더를 나눠야 한다. 다만 기존 세션의 작업 폴더는 **바꿀 수 없고**,
새 폴더에는 **새 세션을 띄워야 한다.** 지금까지 쌓인 맥락을 잃는다.

→ **지금은 하지 않는다.** 아래 방식으로 충분하다. 필요해지면 그때 결정한다.

## 1. 작업 영역을 파일로 나눈다

겹치지 않는 영역에만 손댄다. **자기 영역 밖 파일은 고치지 않는다.**

| 영역 | 파일 | 담당 |
|---|---|---|
| **A 자료·추출** | `tools/extract_catalog.py` · `src/data/catalog/*` · `data/approved/*` | **Claude Code** |
| **B 화면·출력** | `src/features/*` · `src/export/*` · `src/app/App.tsx` · `tests/e2e/*` | **Codex** |
| **C 도메인·가져오기** | `src/import/diagram/*` · `src/domain/quote/*` · `src/app/workspace.ts` | **나중에** |
| **D 문서** | `docs/*` | **계획 세션(나)** |

### 왜 이렇게 갈랐나

A 와 B 는 **파일이 한 개도 겹치지 않는다.** 추출기는 Python 이고 화면은 React 다.
서로 import 하지도 않는다.

C 는 지금 비워 둔다. `src/app/workspace.ts` 가 B 와 겹칠 수 있기 때문이다.
A 와 B 가 끝난 뒤에 한 쪽이 맡는다.

### ⛔ A 의 마지막 단계만은 따로 둔다

A 의 Task 5(`data/approved/*.json` 실제 교체)는 **B 가 끝난 뒤에** 한다.
자료를 바꾸면 SKU 가 전부 달라져서 **B 의 화면 시험과 E2E 픽스처가 함께 흔들린다.**

```
A Task 1~4   추출기 수정·검증 설계·요율 대조·SKU 영향 분석    ← 지금 가능
A Task 5~6   실제 교체와 대조                              ← B 완료 후
```

## 3. 작업 규칙

- **자기 영역 밖 파일을 고치지 않는다.** 고쳐야 하면 먼저 알린다.
- **한 번에 한 세션만 작업한다.** 다른 세션이 작업 중이면 기다린다.
  (같은 폴더라서 동시에 돌리면 서로 덮어쓴다.)
- 각자 **자기 작업만 커밋**한다. 남의 변경을 함께 커밋하지 않는다.
- 커밋 전에 `git status --short` 로 **내 영역 파일만 바뀌었는지** 확인한다.
  다른 영역 파일이 섞여 있으면 멈추고 알린다.
- **푸시는 하지 않는다.** 통합 뒤 한 번에 한다.

## 4. 통합 — Claude Code 가 한다

양쪽 작업이 끝나면 Claude Code 가 아래를 순서대로 한다.

- [ ] `git status --short` 와 `git log --oneline` 으로 **무엇이 들어왔는지** 확인한다.
- [ ] `npm run verify` — 타입 검사 · 전체 단위 시험 · 원가 격리 감사
- [ ] Playwright E2E 전체
- [ ] 실제 Excel 검증 (`tools/verify_in_excel.ps1`) 6조합
- [ ] **영역이 섞이지 않았는지** 확인한다. A 담당이 `src/features/` 를 고쳤거나
      B 담당이 `tools/` 를 고쳤으면 그 이유를 묻는다.
- [ ] 통합 결과를 한 번에 보고한다. **통과한 것과 실패한 것을 나눠서 적는다.**
      "전부 통과"라고 쓰기 전에 실제 출력으로 확인한다.

### ⛔ 통합 담당이 하지 않을 것

- 남의 영역 코드를 **대신 고치지 않는다.** 실패하면 그 영역 담당에게 돌려보낸다.
- 시험을 **지우거나 건너뛰지 않는다.** 실패를 통과로 만들지 않는다.
