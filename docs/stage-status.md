## 카탈로그 추출 결과 (커밋 `71f321b`)

```
제품 1468   판매단가 1444   품셈코드 1347
품셈 항목 1331   매핑 1331   매핑 없음 137

판매단가가 계획서 예상 1442 가 아니라 **1444** 다. 차이 2건(`AUD-0085`, `VCF-0035`)은
**명시적으로 입력된 0원**이다. 설계서 §5.6 의 "0원은 명시적으로 입력된 유효한 0과 구분한다" 에
따라 유효값으로 담았다. 숫자가 늘어난 것이 아니라 **분류가 다르다** — 사전 조사가 `>0` 으로 셌다.

매핑 없음 137 = 품셈 코드 없음 121 + 코드는 있으나 품 값이 없는 16(`PIGTAIL` 8,
CMS 의 `IT 기획자`·`IT PM`·`SW아키텍트` 등 8). 후자도 매핑을 만들지 않고 보고만 한다 —
만들면 노무비 0원이 조용히 들어간다.

## LED 캐비넷 — 확인한 것 (2026-10-05) · **사용자 지시로 보류**

> **보류 (2026-10-05)** — 사용자: *"LED쪽 계산은 나중에 하자"*
>
> 아래 원인 규명과 정정은 **전부 유효하다.** 다만 **지금 고치지 않는다.**
> LED 추출 설계·`CABINET_GROUPS` 수정·IEA/IFR 단종 처리를 **한 묶음으로 나중에** 한다.
>
> **잊으면 안 되는 것** — `CABINET_GROUPS` 에 `IFR` 과 `IWC` 가 빠져 있다.
> LED 캐비넷을 등록하는 순간 **잡자재비가 부풀어 오른다.** 지금은 해당 제품이
> 0건이라 작동하지 않을 뿐이다. **LED 를 다시 다룰 때 이 줄부터 읽는다.**
>
> 누구도 **부분적으로 먼저 고치지 않는다.** 코드만 고치면 추출과 또 어긋난다.


사용자가 `LED 운영라인업 스펙정리_서울영상 송부.xlsx`(제조사 라인업 사양서)를 올려 주었다.
품셈 파일이 아니다. 저장소에 올리지 않았고 내용은 `.local/` 에만 풀어 두었다.

### 결론 둘

1. **`IEA` 는 통째로 단종이고 후속은 `IEA-E` 다** (사용자 확정). 사양서에는 `IE025A` 가
   "운영"으로 적혀 있으나 **사용자 답변이 우선한다.** 품셈에서 세 줄을 단종 시트로
   옮기는 작업은 그대로 남아 있다(결정 D19).
2. **승인 카탈로그에 LED 캐비넷이 0건이다.** `CABINET_GROUPS` 9묶음에 속한 제품도,
   모델코드(`LH0*`·`IE0*`·`IF0*`·`MM0*`·`MP0*`·`SBB-`) 검색도 전부 0건이다.
   잡자재비 LED 제외 규칙은 **코드에 맞게 있으나 제외할 대상이 없다.**
   묶음이 비면 `blocking` 경고가 나므로 조용히 틀리지는 않는다.

### 원인 규명 완료 (2026-10-05, 품셈 원본 수신 후)

사용자가 `원가삭제_2026상반기_표준품셈_260408.xlsx` 를 올려 주었다.
**그 파일의 sha256 이 카탈로그가 기록한 출처 해시와 정확히 일치한다.**

```
업로드 파일        0cc2e8bd3ec9a28bf0622cc71f34901a8793be6ff325e25fa6e785b5826cb85a
catalog-raw.json  0cc2e8bd3ec9a28bf0622cc71f34901a8793be6ff325e25fa6e785b5826cb85a
```

→ **카탈로그를 뽑을 때 쓴 바로 그 파일이다.** 아래 분석이 그대로 적용된다.

#### 원인 — 숨긴 시트가 추출에서 통째로 빠졌다

```
품셈 파일 16시트
  숨김  LED전광판 계산        ⛔ 추출 안 됨   ← LED 캐비넷 0건의 원인
  숨김  단종, 미사용 제품      ⛔ 추출 안 됨   (이쪽은 빠지는 게 맞다)
  보임  품목 12시트           ✅ 추출됨
  보임  간접비 2시트           제외 (의도된 것)
```

`.local/raw/catalog-raw.json` 에 시트가 **12개뿐**이다. 추출이 `sheet_state` 를
어떻게 다루는지는 코드에서 확인하지 못했으나, **결과적으로 숨긴 시트 둘이 없다.**

#### ⚠ 더 큰 문제 — `CABINET_GROUPS` 가 이 파일과 맞지 않는다

`miscMaterials.ts:5` 의 9묶음을 실제 시트 머리글과 대조했다.

| 코드의 묶음 | 이 파일에 |
|---|---|
| `IEA` · `IEA-F` · `MMF` | ✅ 있다 |
| `IEA-E` · `IEA-EF` · `IFR-M` · `IFR-MF` · `MPF` · `MMF-S` | ⛔ **없다** |

반대로 **시트에 있는데 코드에 없는 캐비넷 묶음**이 있다.

```
IFR    32행 — 삼성 IFR P1.5 · P2.5 · IFR-F P1.5 · P2.5
IWC    52행 — 삼성 The Wall IWC P0.84 · P1.26 · P1.68
```

→ **LED 캐비넷이 등록되는 순간 `IFR` 과 `IWC` 가 잡자재비에서 제외되지 않는다.**
  D19 의 근거 자체가 *"견적 1-2 는 174인치 **IFR** P1.5 캐비넷 블록을 건너뛴다"* 였다.
  지금 코드로는 그 IFR 이 합산에 들어가 **잡자재비가 부풀어 오른다.**

**지금은 해당 묶음의 제품이 0건이라 작동하지 않는다. 잠복한 결함이다.**

#### ⛔ D19 의 "IFR 은 단종 시트로 맞게 옮겨졌다" 는 틀렸다

단종 시트 88행을 전부 훑었다. **LED 는 한 건도 없다.** `IFR` 도 없다.
IFR 네 줄은 **현행 `LED전광판 계산` 시트 32~36행에 그대로 있다.**

단종 시트에 실제로 있는 것은 `PV185S`(7행)·HDMI 케이블류·무선마이크·TV·
밀리터리 광케이블·프로젝터 등이다.

#### LED 시트는 품목 목록이 아니라 **계산 시트**다

다른 12시트와 성격이 다르다. 그냥 추출하면 안 된다.

```
 6행   "000인치 삼성 LED전광판 (0x0)"    ← 자리표시용 행
11·12행  #REF!                          ← 끊어진 참조
15·16행  같은 제품이 두 줄, 가격이 다름     (38,472,000 / 34,000,000)
57행    묶음은 MMF 인데 품명은 IWC 제품
수량 칸  대부분 비어 있음                 (계산용 틀이라서)
```

→ **추출 규칙 설계가 먼저다.** 숨김 해제만으로 해결되지 않는다.

### IEA 세 줄 옮기기 — 지금은 하지 않았다

사용자가 *"제가 하겠습니다"* 로 나에게 맡겼으나, **지금 옮겨도 카탈로그는 바뀌지 않는다.**
`LED전광판 계산` 과 `단종, 미사용 제품` **둘 다 추출되지 않기 때문**이다.
한쪽에서 다른 쪽으로 옮기는 것은 현재 아무 효과가 없다.

또 이 파일에는 수식과 `#REF!` 가 섞여 있어 **openpyxl 로 다시 저장하면 원본이 상할 수 있다.**
효과가 없는 작업에 그 위험을 지지 않는다. **추출 설계가 정해진 뒤에 한다.**

## D23 출력 차단 — 아직 검증되지 않았다 (2026-10-05)

계획 세션이 *"현행 코드가 이미 맞다, 바꿀 코드 없음"* 으로 **잘못 종결했다가 철회했다.**

```

지금은 아무것도 내려받을 수 없으므로 **차단 동작이 시험된 적이 없다.**

## 계획을 쓸 때 전제로 깔 사실

### 간접비 28~30행은 "원본 그대로 상수 0"으로 이미 구현됐다

원본 실측 (시스템 시트 5개 전부 동일):

```
28행 연금보험료         E28 = 0.01215   J28 = 0   ← 상수, 수식 아님
29행 건강보험료         E29 = 0.00957   J29 = 0   ← 상수
30행 노인장기요양보험료  E30 = 0.00124   J30 = 0   ← 상수
```

나머지 6개(간접노무비·고용보험료·산재보험료·산업안전보건관리비·퇴직공제부금비·공과잡비)는 `=INT(...)` 수식.

구현:

```ts
interface IndirectCostRule {
  rate: DecimalText;   // 0.01215 — 미적용이어도 보존
  applied: boolean;    // false
  basis: IndirectBasis;
  source: string;
}
```

`applied: false` 면 exporter 가 J열에 **상수 0** 을 쓰고 수식을 쓰지 않는다. 요율은 E열에 남는다.
기본값은 원본과 동일(적용 6 / 미적용 3)이며 **자동으로 켜지 않는다.**

`mapping.md` Ruling R3:

> 요율은 적혀 있으나 금액 칸이 상수 0 이다. **이 견적 1건에서 미적용이라는 뜻이지 법정 미적용이 아니다.**

→ **발주처 프로파일(O7) 설계의 출발점.** `IndirectCostRule[]` 이 시스템마다 붙어 있으므로,
프로파일은 "이 배열을 통째로 갈아끼우는 것"이면 깔끔하다. 시스템별로 다른 프로파일도 이미 가능하다.

### 직접비계 SUM 은 항상 첫 품목 행부터 쓴다

원본은 시트마다 시작 행이 다르다(G5/G6/G7). 그룹 머리글 행에 숫자가 없어 결과는 같지만
일관성이 없다. 생성기는 **항상 첫 품목 행**부터 쓴다 (`mapping.md` R2).

### 노임 단위 불일치는 차단하되 던지지 않는다

품셈 항목의 단위와 노임 단위가 어긋나면 `wage-unit-mismatch` + `blocking: true` 경고를 세우고,
해당 직종 금액과 적용 단가를 **0 으로 둔다.** 조용히 환산하지 않는다 — 환산은 사람이 지정한
`conversionFactor` 만 쓴다. 던지지 않는 이유: 1,468건 중 한 건 때문에 카탈로그 빌드 전체가
멈추면 안 되고, 사용자가 봐야 하는 것은 "이 제품 하나가 막혔다"이기 때문. 커밋 `1701584`.

### Task 완료 조건은 "테스트 통과"가 아니라 "typecheck + 테스트 + audit"이다

실제로 물린 사례. `InternalLine` 에 `sellingUnitPrice` 가 없어서 내부용 표의
**판매단가 열이 통째로 비어 있었다.** 테스트 12개가 전부 통과했고 Excel 검증도 통과했다.
빈 셀은 유효한 XML 이라 어디서도 안 걸린다.

잡은 것은 `tsc -p tsconfig.app.json --noEmit` 하나뿐이다
(`noUncheckedIndexedAccess`, `exactOptionalPropertyTypes` 를 켜 둔 덕).

→ **새 계획의 각 Task 완료 조건에 "테스트 통과"만 쓰지 않는다.**
   `npm run verify`(typecheck → test → audit:exports)로 적는다.
   테스트만으로는 **"값이 아예 안 들어간"** 종류를 못 잡는다. 틀린 값은 테스트가 잡지만,
   없는 값은 테스트가 애초에 쳐다보지 않는다.

### 내부용 → 고객용 방향은 한쪽뿐이다

내부용은 고객용 통합문서에 원가 시트를 **덧붙인다**. 내부용에서 뭔가를 지워 고객용을 만드는
경로가 코드에 **없다**. 지우는 방식은 하나만 빠뜨려도 원가가 고객에게 간다.
설계서 §8.7 "원가 통합문서를 만든 후 열만 숨겨 고객용으로 보내지 않는다" 의 구현이다.

`buildQuoteWorkbook` 의 `extraSheets` 옵션을 고객용 경로는 넘기지 않으며, 시트 수 검사가 고정한다.
새 출력 경로를 만들 때 이 방향을 뒤집지 않는다.

### ☠ `laborMode: 'not-applicable'` 을 "모를 때의 기본값" 으로 쓰지 않는다

구성도 변환에서 실제로 물린 함정이다. **다섯 번째로 나온 "조용히 틀리는" 계열**이고,
금액 비중으로는 가장 크다.

구성도는 품셈을 모른다. 그래서 모든 행을 `'unresolved'` 로 두면 `calculateQuote` 가
`labor-unresolved` blocking 을 전 행에 세운다. 당연하다.

**`'not-applicable'` 로 바꾸면 통과한다. 그게 함정이다.**

```
not-applicable → 노무비 0
              → 간접비 6항목이 "노무비 대비"
              → 간접비까지 0
              → 공과잡비도 0 (직접비 + 간접노무비 + 산업안전 기준)
```

실물 측정 — 3,540만원 견적에서 **노무 194만 + 간접비 431만 = 625만원(18%)** 이 사라진다.
그리고 **아무 경고도 안 난다.** `not-applicable` 은 정상 상태다.

> `'not-applicable'` 은 "노무비를 모른다" 가 아니라 **"이 품목에는 노무비가 없다" 는 단정**이다.
> 모르면 `'unresolved'` 로 막는다.

올바른 처리: 카탈로그 제품이 `laborMappingId` 를 가지면 `'mapped'` 로 심고,
`calculateLaborForRows` 로 단가를 만들어 `calculateQuote(doc, { laborUnitPrices })` 에 넘긴다.
**계산 엔진은 고치지 않는다.** 품셈이 없는 제품만 `'unresolved'` 로 남긴다.

`buildLaborReference()`(`src/data/catalog/load.ts`)가 품셈·노임·매핑 세 파일을 읽고
`sourceSha256` 이 셋 다 같은지 확인한다. **가격과 달리 셋 다 필수**다 — 없으면 위 문제가 그대로 난다.

### 🚫 옵션 카드 id 역산은 불가다 — 다시 조사하지 말 것 (O15)

av-builder 가 `selectedOptionQuantities: {"eqopt-xlsx-454": 4}` 만 내보내고 그 id 가 **어떤 제품인지는
안 내보낸다.** 우리 쪽에서 카탈로그 행 번호로 역산할 수 있을지 **조사했고 기각했다.**

가설: 옵션 id 의 숫자가 부모 장비 바로 뒤 번호다(`eq-xlsx-451` 의 옵션이 `454`/`456`).
그렇다면 `av-builder N + 보정값 = 카탈로그 행` 이 성립할 수 있다.

유일 매칭 **558쌍**으로 검증:

```
시트별 (카탈로그 행 − av-builder N) 차이
  오디오      182건  61가지
  영상        153건  72가지
  프로젝터      69건  15가지
```

보정값이 흩어진다. 더 결정적인 것은 **같은 장비 안에서도 어긋난다**:

> XDM-12 기준 보정 −313 이면 `456 → 12G-SDI input card`(입력 ✓)인데
> `454 → HDMI input card`(입력 ✗ — 엣지에서 **출력** 포트로 쓰인다).
> 출력 카드는 한 행 뒤라 보정값이 −312 여야 한다. **자기모순이다.**

→ **역산 불가 확정.** 유일한 해결은 av-builder 가 `options` 배열을 내보내는 것이다
   (`docs/interface/av-builder.md` §2). 그때까지 변환기는 **행을 만들되 제품 미상 +
   `blocking` 경고**로 둔다. 행을 빼면 카드 15줄(74만~190만원/장)이 조용히 사라진다.

**이 조사를 반복하지 말 것.** 숫자가 가까워 보여서 누구나 한 번은 시도하게 된다.

### ⏰ SKU 는 원본 행 번호다 — 품셈 파일이 개정되면 깨진다 (O12)

SKU 가 `시트코드-원본행번호` 다 (`CBL-0006`). **원본에서 행이 하나라도 밀리면 SKU 가
다른 제품을 가리킨다.**

지금은 아무 문제가 없다. 품셈 파일이 한 번도 개정되지 않았기 때문이다.
**26년 하반기 품셈이 나오는 순간 터진다.** 저장해 둔 견적 문서를 다시 열면 `CBL-0006` 이
어제와 다른 제품이 되어 있고, 조용히 바뀐다.

설계서 §6.3 이 이미 금지한 것이다:

> 다시 열 때 새 카탈로그로 조용히 가격을 바꾸지 않는다. 명시적인 업데이트·차이 확인을 제공한다.

**현재 방어선은 없다.** 감지조차 안 된다. 실측:

```
grep -rn "versions" --include="*.ts" src/ | grep -v quote/types.ts
  → calculate.ts:122  타입 선언
  → calculate.ts:195  document.versions 를 스냅샷에 복사
  → projection.ts:102 주석
  비교하는 코드 없음
```

`QuoteDocument.versions` 는 **쓰이기만 하고 아무도 읽지 않는다.** 그리고 설계서 §10.4 의
`serializeDraft` 가 아직 없다 — **작업 파일 저장·불러오기 자체가 미구현**이라 비교할 시점이
없다. "감지는 되는데 해결이 안 됨"이 아니라 **아무것도 없음**이다. 있는 줄 알고 기대면 안 된다.

품셈 파일이 개정돼 새 `products.json` 이 나와도 **구버전이 git 이력에 남는다.**
두 파일을 `options.sheet` + `quoteName` + `quoteSpec` + `unit` 로 맞추면 구↔신 대조표를
**나중에** 만들 수 있다. 지금 제품에 별도 지문 필드를 심어둘 필요가 없다.

→ **"지금 SKU 체계를 안 바꾸면 끝장"이 아니다.** 시한은 여전히 "품셈 개정 전"이지만,
   급하게 바꿔서 지금 멀쩡한 1,468건을 흔들 이유는 없다. 결정 D3 의 "되돌릴 수 있게"와 같은 성격이다.

### 독립 과제로 두지 말고 "작업 파일 + 차이 화면"에 넣는다

작업 파일 저장·불러오기가 **아직 없다는 것이 오히려 기회다.** 나중에 끼워 넣는 대신
처음부터 설계에 넣을 수 있다.

설계서 §6.3 이 이미 요구한다:

> 다시 열 때 새 카탈로그로 조용히 가격을 바꾸지 않는다. **명시적인 업데이트·차이 확인을 제공한다.**

이 화면은 **어차피 만들어야 한다** — 카탈로그 가격이 바뀌기만 해도 필요하다.
SKU 변경은 그 화면이 다루는 여러 차이 중 하나일 뿐이다. 별도 메커니즘을 만들지 않는다.

생각해 둘 방향 (아직 결정 아님):
- 견적 문서를 열 때 카탈로그 원본 해시가 다르면 **차이 화면** — 설계서 §6.3 문면에 가장 가깝다
- 개정 시 **구↔신 대조표**를 만들어 배포 (git 의 구 `products.json` 에서 생성)
- 행 번호 대신 **품명+규격 해시**를 SKU 로 — 행이 밀려도 안정적이지만 품명 오타 수정에 깨진다. 우선순위 낮음

→ 품셈 파일이 실제로 개정되기 **전에** 정한다.

### 원본 데이터의 셀 안 줄바꿈을 확인한다 (결함 D8)

카탈로그 규격 칸에 줄바꿈이 든 제품이 **112건** 있었다.

```
H_4xHDMI  output  card⏎(HDMI  1.4  -  Dual  Link)
5C-CRIMP⏎ F-5C
In : 40Mono⏎Out : 25Bus⏎Total : 65ch
```

견적 양식은 행 높이가 **21pt 고정**이라 둘째 줄이 **조용히 잘린다.** 화면에도 인쇄물에도
한 줄만 나온다. **어떤 검사에도 안 걸린다** — 파일은 정상으로 열리고, 수식 오류 0, XML 유효
(줄바꿈은 합법적인 텍스트), 웹↔Excel 금액 대조도 통과(금액을 안 건드리니까).

조치: `flattenLineBreaks()` — 줄바꿈과 주변 공백을 공백 하나로 눕힌다. 내용이 사라지지 않고
한 줄에 전부 보인다.

택하지 않은 쪽: `wrapText` 서식으로 줄바꿈을 살리는 것. `xl/styles.xml` 을 건드려야 하는데
설계서 §9.1 "원본 서식을 그대로 옮긴다" 를 깬다. 서식 보존이 이 프로젝트의 핵심 전제라
거기를 흔드는 대신 내용을 눕혔다.

→ **새 원본을 읽는 계획마다 셀 안 줄바꿈을 조사하는 단계를 넣는다.** 수식 셀 형태 조사와
   같은 성격이다.

### 절사 지점에서는 변화량이 절사 단위보다 커야 한다

편집 재계산 테스트가 수량을 `+1` 만 올렸더니 **거짓 실패**가 났다. 단가가 작은 품목이 걸려
200원 변화가 **만원 미만 절사에 먹혔다.** "수량 수정이 갑지에 반영되지 않았다" 고 나왔지만
수식은 멀쩡했다.

→ 변화량을 절사 단위보다 크게 잡고, **절사가 없는 직접비계도 함께 확인**한다.
   절사가 있는 지점을 통과시키는 테스트는 이 함정을 항상 깔고 있다.

### 행 잘림 검사는 내역 시트로만 건다

AutoFit 기준 잘림 판정에서 갑지 8행(`금  액 :`)과 마지막 행이 걸렸다. **원본 견적서를 같은
방법으로 재어 보니 원본도 같았다** (갑지 8행 24→26.5 원본 / 24→26 생성물).
회사 양식 자체의 설계이지 생성기 결함이 아니다.

→ 검사를 **내역 시트로** 좁힌다(반복 머리글 유무로 식별). 데이터 길이에 따라 달라지는 것은
   품목 행이고, 거기서는 잘림 0 이다.
→ 일반 원칙: **생성물이 이상해 보이면 원본을 같은 방법으로 재어 본다.** 원본도 그렇다면
   재현해야 할 사양이지 고칠 결함이 아니다.

### ☠ 정규식에 `\b` 를 쓸 때 **백스페이스 문자로 굳는다** — 이 저장소에서 네 번 물렸다

커밋 `2019054` 의 `tools/costLeakScan.ts` 에서 실제로 일어난 일이다.

```
쓰려던 것   /<c\b([^>]*)>…/      \b = 단어 경계
파일에 들어간 것  /<c<0x08>([^>]*)>…/   0x08 = 백스페이스 문자
```

XML 에 `<c` 뒤에 백스페이스가 올 리 없으므로 **셀을 한 칸도 순회하지 못했다.**
원가 유출 검사가 **항상 빈 결과**를 돌려주는 상태로 커밋됐다.

**눈으로는 구분되지 않는다.** 편집기에서도, `git diff` 에서도 똑같아 보인다.
`cat -A` 로 봐야 `^H` 가 드러난다.

#### 대처

- 정규식에서 **`\b` 를 쓰지 않는다.** 전방탐색으로 바꾼다 — `<c(?=[ />])` 처럼 의도를 글자로 적는다
- 파일을 쓴 뒤 `python -c "print(sum(1 for b in open(F,'rb').read() if b==8))"` 로 확인한다
- 같은 계열: `\0` `\v` `\f` `\a` 도 제어 문자로 굳을 수 있다

#### ★ 원인을 찾았다 — 도구 경로가 백슬래시를 한 겹 벗긴다 (2026-10-04)

부주의가 아니다. **셸 heredoc 이 인용 부호를 써도 백슬래시를 하나 먹는다.**

```
스크립트에 쓴 것      b'\\b'      ← 백슬래시 + b 를 의도
파이썬이 받은 것      b'\b'       ← 0x08 제어 문자
```

그래서 *"제어 문자를 글자로 바꾸는"* 치환 스크립트가 **제어 문자를 제어 문자로 바꾸는**
꼴이 되어 두 번 연속 실패했다. 바꾼 개수는 8 이라고 나오는데 파일은 그대로였다.

같은 계열로 `\u` 가 들어간 경로 문자열(`.paseo\uploads`)에서도
`UnicodeEncodeError: truncated \uXXXX escape` 가 난 적이 있다.

##### 우회법

```python
BS = chr(92)        # 또는 bytes([92])
M = {8: BS + 'b'}   # 리터럴로 쓰지 않는다
```

**백슬래시를 리터럴로 쓰지 말고 코드값으로 만든다.** 경로는 슬래시(`/`)를 쓴다.

##### 이 함정을 이 저장소에서만 다섯 번 밟았다

구현 담당이 네 번(`costLeakScan.ts` 의 `\b` 포함), 계획 담당이 한 번이다.
계획 담당의 사례는 **이 경고문을 쓰다가 경고문 안에 제어 문자를 넣은 것**이다.
`grep` 이 `docs/stage-status.md` 를 이진 파일로 보고 검색을 거부해서 발견됐다.

##### 파일을 쓴 뒤 확인한다

```python
sum(1 for b in open(F,'rb').read() if b < 9 or 11 <= b <= 12 or 14 <= b <= 31)
```

0 이 아니면 제어 문자가 들어간 것이다. **눈으로는 안 보인다.**

#### 이걸 드러낸 것은 모델이 아니라 **역방향 시험**이다

```
tests/integration/costLeak.test.ts
  "판매 칸 목록을 비우면 같은 값이 전부 걸린다 — 검사가 죽어 있지 않다"
```

검사기가 **반드시 뭔가를 찾아내야 하는 상황**을 만들어 두고, 못 찾으면 실패시킨다.
이 시험이 없었으면 764개 테스트가 통과하면서 *"유출 0건"* 이 그대로 보고됐다.

→ **검사기·감사기 계열에는 "검사가 살아 있는지" 확인하는 시험을 반드시 둔다.**
   "아무것도 안 나와야 한다" 쪽 시험만 있으면, 검사기가 죽어도 전부 통과한다.

### 수식 셀은 형태를 먼저 조사한다

카탈로그 추출에서 실제로 물린 함정이다. 품 열에 `=0.23*80%`, `=0.63*(1+(2-1)*30%)`,
`=(0.46+0.33+0.52)*(1+(2-1)*30%)` 같은 식이 **585건** 있었다. 전부 **셀 참조가 없는 순수 산술식**이다.

수식이라는 이유로 건너뛰면 제품 약 1/3 의 노무비가 조용히 0 이 된다. 터지지 않고 틀리는 종류다.

해결: `eval` 을 쓰지 않고 숫자 리터럴만 받는 재귀하강 파서로 푼다. 식별자가 하나라도 나오면
(`=T6*U$3`, `=SUM(A1:A3)`) 거부한다. 설계서 §5.1 의 "JavaScript `eval` 로 파일의 수식을
실행하지 않는다" 를 지킨다.

→ **새 원본을 읽는 계획을 쓸 때마다 "그 열의 수식 셀이 어떤 형태인지" 를 먼저 조사하는 단계를 넣는다.**
   수식 셀의 존재만 확인하고 형태를 안 보면 같은 함정에 다시 빠진다.

### B열 머리글은 브랜드가 아니다

`classifyRow` 가 `brand` 로 분류하는 행의 실제 값 289종을 보니 `DP to HDMI 케이블&젠더`,

→ 브랜드가 정말 필요하면 별도 입력이 필요하다 (O10).
